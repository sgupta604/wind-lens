## Problem Summary

On-device testing of the location-picker feature revealed **4 bugs** with a single root cause pattern (UI code reads `stablePositionProvider` instead of `effectivePositionProvider`) and **1 UX enhancement** request (show current location source on dome/AR screens).

All bugs are UI-layer issues. The core data flow (provider graph, wind fetching, horizon fetching) is correctly wired through `effectivePositionProvider`. The UI simply checks the wrong provider for display/null-guard purposes.

## Fix Details

### BUG 1: Reset to GPS button unresponsive

**File:** `lib/features/location_picker/location_picker_screen.dart`, lines 67-76
**Root cause:** `_onResetToGps()` reads `stablePositionProvider` which is null when GPS has not resolved. The `if (gps != null)` block silently skips -- no feedback to user.
**Fix:** Read `effectivePositionProvider` for the map snap (so it works when override is set even without GPS). Add `else` branch with SnackBar fallback if both GPS and override are null ("Waiting for GPS signal...").

Before:
```dart
void _onResetToGps() {
  ref.read(locationOverrideProvider.notifier).clear();
  final gps = ref.read(stablePositionProvider);
  if (gps != null) {
    setState(() {
      _selectedPosition = LatLng(gps.latitude, gps.longitude);
    });
    _mapController.move(_selectedPosition, _mapController.camera.zoom);
  }
}
```

After:
```dart
void _onResetToGps() {
  ref.read(locationOverrideProvider.notifier).clear();
  final gps = ref.read(stablePositionProvider);
  if (gps != null) {
    setState(() {
      _selectedPosition = LatLng(gps.latitude, gps.longitude);
    });
    _mapController.move(_selectedPosition, _mapController.camera.zoom);
  } else {
    if (mounted) {
      ScaffoldMessenger.of(context).showSnackBar(
        const SnackBar(
          content: Text('Waiting for GPS signal...'),
          duration: Duration(seconds: 2),
        ),
      );
    }
  }
}
```

Note: We keep `stablePositionProvider` here (not `effectivePositionProvider`) because the intent of "Reset to GPS" is specifically to snap back to the raw GPS position. After `clear()`, the effective position IS the stable position. The snackbar handles the edge case where GPS has not resolved.

### BUG 2: Re-entering map goes to 0,0 and locks

**File:** `lib/features/location_picker/location_picker_screen.dart`, lines 35-43
**Root cause:** `initState()` reads `stablePositionProvider` (raw GPS), not `effectivePositionProvider`. On re-entry after setting an override with no GPS, falls back to (0,0).
**Fix:** Change to `ref.read(effectivePositionProvider)` so the map opens at the override location if one is set, falling back to GPS, then to (0,0).

Before:
```dart
final gps = ref.read(stablePositionProvider);
```

After:
```dart
final position = ref.read(effectivePositionProvider);
```

The import for `location_override_provider.dart` is already present (line 8).

### BUG 3: Location override does not update wind data (UI overlay hides it)

**File 1:** `lib/features/wind_dome/wind_dome_screen.dart`, line 166
**File 2:** `lib/features/ar_view/ar_view_screen.dart`, line 169

**Fix 3b (AR):**

### BUG 4: Permanent "waiting for GPS" text

**Same root cause as BUG 3.** `DataStatusBar` receives `hasPosition: position != null` from `ARViewScreen`, which derives `position` from `stablePositionProvider`. Fix 3b resolves this automatically. `DataStatusBar` itself needs no changes -- it is a dumb widget.

Similarly, `WindDomeScreen` line 254 checks `if (position == null)` using the same `position` variable. Fix 3a resolves this.

### UX Enhancement: Location indicator on dome and AR screens

**Request:** Show whether the user is using GPS or a custom location on the dome screen and AR screen.

**Implementation:** Create a small `LocationIndicatorChip` widget that reads `locationOverrideProvider` and `effectivePositionProvider`:
- When override is set: show custom coordinates (e.g., "40.71, -74.01")
- When override is null: show "GPS" (or GPS coordinates if available)

**Placement:**
- **Dome screen:** Below the `DomeInfoBar`, as a small chip aligned left
- **AR screen:** In the `DebugPanel` (already shows latitude/longitude). Also add a small chip near the top-right when override is active, so users without debug panel can see it.

For simplicity in this fix round, we will add the chip to the dome screen only (most visible, most requested), and update the AR screen DebugPanel to show "GPS" vs "Override" label next to the existing lat/lng display. A standalone chip on the AR screen can be added later if needed.

**Widget design:**
```dart
class LocationIndicatorChip extends ConsumerWidget {
  // Reads locationOverrideProvider + effectivePositionProvider
  // Shows "GPS" or "lat, lng" with a pin icon
  // Semi-transparent black pill, matching existing dome UI styling
}
```

**File:** `lib/features/wind_dome/widgets/location_indicator_chip.dart` (new)
**Test:** `test/features/wind_dome/widgets/location_indicator_chip_test.dart` (new)

## Implementation Notes

### Decisions

1. **Keep `stablePositionProvider` in `_onResetToGps`:** The intent of "Reset to GPS" is to go back to GPS, not to the effective position (which could be the override). After `clear()`, effective = stable anyway. The snackbar covers the GPS-unavailable edge case.

2. **DebugPanel lat/lng source:** The `DebugPanel` already receives `latitude` and `longitude` from the parent `ARViewScreen`. Currently these come from `stablePositionProvider` (line 233-234). After the fix, they will come from `effectivePositionProvider`. No DebugPanel code changes needed, just the parent passing different values.

3. **LocationIndicatorChip is a ConsumerWidget:** It reads providers directly rather than accepting constructor parameters. This keeps the parent screens clean and makes the chip self-contained.

4. **Dome screen only for chip (MVP):** The UX enhancement chip goes on the dome screen first. The AR screen already shows coordinates in the debug panel. A dedicated AR chip can be added in a future pass.

### Patterns Used

- Same `effectivePositionProvider` pattern already established in data providers
- SnackBar for user feedback (standard Flutter pattern)
- ConsumerWidget for location chip (reads providers directly)
- Semi-transparent black pill styling (matches dome info bar and existing UI)

### Risk Assessment

| Risk | Impact | Likelihood | Mitigation |
|------|--------|------------|------------|
| Existing test regression from provider swap | High | Very Low | effectivePosition == stablePosition when no override (all existing tests have no override set) |
| AR screen import conflict | Low | Low | Using package import format already used in ar_view_screen.dart |
| SnackBar not visible on dark background | Low | Low | Default SnackBar has visible styling; can customize if needed |
