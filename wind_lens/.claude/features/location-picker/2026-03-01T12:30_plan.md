## Architecture Overview

### Current Position Data Flow

```
DeviceSensorService.positionStream
  --> gpsPositionProvider (Stream<PositionData>)
    --> StablePosition (debounces >100m)
      --> windDataProvider
      --> horizonProfileProvider
      --> sceneStateProvider
      --> domeWindProfileProvider
```

### Proposed Position Data Flow

```
DeviceSensorService.positionStream
  --> gpsPositionProvider (Stream<PositionData>)
    --> StablePosition (debounces >100m)
          |
          v
locationOverrideProvider (PositionData? -- user-set, session-only)
          |
          v
effectivePositionProvider = override ?? stablePosition
          |
          +----> windDataProvider
          +----> horizonProfileProvider
          +----> sceneStateProvider
          +----> domeWindProfileProvider
```

The key insight: we insert ONE provider indirection layer (`effectivePositionProvider`) between the GPS chain and all data consumers. This is a single-point change that routes all position-dependent data through the same override mechanism.

### Sensor Data Flow (UNCHANGED)

```
DeviceSensorService.sensorStream
  --> rawSensorProvider (Stream<SensorState>)
    --> sensorNotifiersProvider (ValueNotifier heading/pitch)
```

Sensor data (compass heading, pitch) is NOT affected by the location override. The user overrides where they want wind data FROM, not where they physically are.

### Navigation Flow

```
HomeScreen
  --> HomeTopBar [LOC button]
    --> Navigator.push(LocationPickerScreen)
      --> User taps map to place pin
      --> User taps "Confirm"
        --> locationOverrideProvider.set(selectedPosition)
        --> Navigator.pop()
      --> User taps "Cancel"
        --> Navigator.pop() (no change)
      --> User taps "Reset to GPS"
        --> Pin snaps to GPS location
```

```
            |

                 |
                 +-- Row
                      +-- "Reset to GPS" TextButton
                      +-- "Confirm" ElevatedButton
```

### State Management

**LocationPickerScreen local state:**
- `LatLng _selectedPosition` -- the pin position on the map (starts at GPS or fallback)
- Initialized from `ref.read(stablePositionProvider)` in `initState`
- Updated on every map tap via `onTap` callback
- Written to `locationOverrideProvider` only on "Confirm"

**Provider state (global, session-only):**
- `locationOverrideProvider` -- `PositionData?`, null by default (use GPS)
- `effectivePositionProvider` -- computed: returns override if set, otherwise stablePosition

### HomeTopBar Changes

```
HomeTopBar (StatefulWidget)
  |
  +-- Row (button row, right side)
       |
       +-- [NEW] LOC button (pin icon, outline style matching DOME)
       +-- DOME button (existing)
       +-- LIVE AR button (existing)
```

The LOC button uses a `Icons.location_on_outlined` icon or "LOC" text, styled identically to the DOME button (outlined pill shape). When the location override is active, the button could optionally change color (nice-to-have, not MVP-critical).

## Data Model Changes

**No database or model changes required.** The existing `PositionData` Freezed model already contains all fields needed (latitude, longitude, altitude, accuracy, timestamp). The override provider simply holds an optional `PositionData?`.

For the map tap, we construct a `PositionData` from the `LatLng`:
```dart
PositionData(
  latitude: tappedLatLng.latitude,
  longitude: tappedLatLng.longitude,
  altitude: 0.0,     // Not meaningful for override
  accuracy: 0.0,     // Manual selection, no GPS accuracy
  timestamp: DateTime.now(),
)
```

## Provider Design Detail

### locationOverrideProvider (new, codegen)

```dart
@riverpod
class LocationOverride extends _$LocationOverride {
  @override
  PositionData? build() => null;  // No override by default

  void set(PositionData position) {
    state = position;
  }

  void clear() {
    state = null;  // Revert to GPS
  }
}
```

### effectivePositionProvider (new, codegen)

```dart
@riverpod
PositionData? effectivePosition(EffectivePositionRef ref) {
  final override = ref.watch(locationOverrideProvider);
  if (override != null) return override;
  return ref.watch(stablePositionProvider);
}
```

## Implementation Notes

### Design Decisions

1. **Separate file for override providers:** `location_override_provider.dart` lives in `lib/core/providers/` alongside the other provider files. Both `locationOverrideProvider` and `effectivePositionProvider` are in the same file since they are tightly coupled.

2. **Codegen (@riverpod) for new providers:** Consistent with the existing pattern used by `stablePositionProvider`, `windDataProvider`, etc. This means running `build_runner` after creating the file.

3. **Non-codegen dome provider:** `domeWindProfileProvider` in `dome_providers.dart` uses manual `FutureProvider<T>((ref) {...})` syntax (not codegen). The change there is just swapping `stablePositionProvider` to `effectivePositionProvider` in the `ref.watch()` call -- no codegen involved for that file.

4. **LOC button placement:** Left of DOME button in the top bar row. Uses the same outlined pill style as DOME for visual consistency.

5. **Map initial center:** Read `stablePositionProvider` (GPS) on screen open. If null (no GPS fix yet), fall back to (0, 0). This is an edge case for the MVP.

6. **Confirm-only writes:** The override provider is only set when the user taps "Confirm". Tapping around the map updates local state only. This prevents unnecessary API calls while exploring.

7. **No persistence:** `locationOverrideProvider` starts as `null` on each app launch. Session-only by design.

### Patterns Used

- **Riverpod codegen** (@riverpod annotation + build_runner) for new providers
- **ConsumerStatefulWidget** for LocationPickerScreen (needs ref + local state)
- **Navigator.push(MaterialPageRoute)** for screen navigation (same as AR view, Wind Dome)
- **GoogleFonts.dmMono** / **GoogleFonts.bebasNeue** for text styling
- **Dark theme** with black background, white/grey text
- **Semantics** labels on all interactive elements

### Trade-offs

| Decision | Alternative | Why This Way |
|----------|-------------|--------------|
| Session-only persistence | SharedPreferences | User confirmed session-only; simpler, no storage permission |
| Full-screen map page | Bottom sheet | Consistent with existing navigation (AR view, Dome) |
| Confirm-only writes | Write on every tap | Avoids unnecessary API calls during exploration |
| LOC button in top bar | FAB or bottom bar | Matches existing button row pattern (DOME, LIVE AR) |
| Single file for both providers | Two separate files | They are tightly coupled; simpler imports |
