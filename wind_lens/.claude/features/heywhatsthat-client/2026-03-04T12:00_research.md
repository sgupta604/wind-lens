## API Verification (Live Testing 2026-03-04)

**All 3 endpoints tested with real curl requests. Several SPEC-003 corrections discovered.**

### Submit (`query.cgi`) — VERIFIED
```
Request: GET https://www.heywhatsthat.com/bin/query.cgi?lat=47.6062&lon=-122.3321&elev=2&elev_is_absolute=0&name=windlens_test&public=0&return_data=1
Response: RDJCX2LU queued 47.6062 -122.3321 - 2 1772595803 0 0 0 0 wt windlens_test
Status: 200
```
**SPEC-003 CORRECTION:** Panorama ID is **token[0]** (first token), NOT token[1] (second). Second token is `queued`.
- Spec said: `ok PANORAMA_ID_HERE ...` — WRONG
- Actual: `PANORAMA_ID queued lat lon ...`
- Parse as: `response.body.trim().split(' ')[0]`

### Poll (`results/{id}/data`) — VERIFIED
```
Not ready: "running 46.8523 -113.9876 984 2 ..." (status 200)
Ready:     "ok 47.6062 -122.3321 62 2 ..."      (status 200)
Invalid ID: 404 HTML page
```
**SPEC-003 CORRECTION:** When not ready, body is NOT empty/whitespace. It starts with `running`.
- Check for `ok` prefix is correct; everything else means not ready.
- Invalid IDs get 404, not empty body.

### Computation Time — VERIFIED
- Seattle (urban, possibly cached): ~2 seconds
- Montana wilderness (uncached): ~9 seconds
- **SPEC-003 said "~2 minutes" — actual is 5-15 seconds for tested locations**
- May vary for complex/mountainous terrain; keep 5-minute timeout as safety net

### Result (`result.json`) — VERIFIED
```
Status: 200 (valid ID), 200 with empty body (invalid ID)
Invalid ID header: X-App-Status: 460 Unknown panorama, Content-Length: 0
```
- Exactly **360 `limits` entries** — confirmed for both Seattle and Montana
- Each entry: `[lat, lon, elevation_angle_degrees]` — confirmed
- `declination` present (integer): Seattle=15, Montana=13
- `peaks` array present with named features
- All standard JSON fields present: id, lat, lon, elev_amsl, elev_agl, refraction, image, etc.

**IMPORTANT:** Invalid panorama ID returns HTTP 200 with empty body (not 404). Must check body is non-empty before `jsonDecode`.

### Patterns to Follow

1. **HTTP client injection** -- Same as `WindApiClient`: accept optional `http.Client` in constructor, test with `MockClient` from `http/testing.dart`
2. **Graceful degradation** -- Same as wind API: on any failure return a valid zero/flat result, never throw to the caller
3. **Constants class** -- Same as `WindApiConstants`: static const URLs, timeouts, parameter names
4. **Provider wiring** -- Same swap-point pattern: change one `return` statement in `service_providers.dart`
5. **Dispose pattern** -- Register `ref.onDispose()` for the HTTP client in the provider

### HorizonProvider Interface Signature Note

The existing `HorizonProvider` interface uses named parameters:
```dart
Future<HorizonProfile> getHorizon({
  required double latitude,
  required double longitude,
});
```

The SPEC-003 code examples use positional parameters (`getHorizon(double lat, double lng)`). The implementation MUST match the actual interface signature with named parameters.

## Constraints

### Performance
- HeyWhatsThat panorama computation takes ~2 minutes server-side
- Polling every 10 seconds = up to ~30 HTTP requests during the wait
- `CachedHorizonProvider` prevents re-fetching within ~111m of same location
- Disk cache means subsequent app launches skip the 2-minute wait entirely
- `HorizonProfile` is a Freezed model (not hot-path) -- overhead is acceptable

### Platform
- iOS 14.0+, Android API 24+
- No new platform permissions needed (GPS already granted via P2B-001)
- No new native dependencies

### Network
- HeyWhatsThat API is HTTP (no auth required for low-volume use)
- 5-minute timeout for panorama computation
- Must handle offline / unreachable scenarios gracefully

### API Limitations
- SRTM coverage: 60N to 54S latitude only (no Arctic/Antarctic)
- Terrain only -- no buildings, trees, or man-made structures
- Low-volume use acceptable for development; contact HWT for production scale
- No rate limit documented, but their frontend polls at 10s intervals

### Dependencies
- `http: ^1.6.0` -- already in pubspec, no new packages needed

### Complexity
- **Level:** Medium
- **Rationale:** The architecture is already built (interface, cache, provider wiring). The main work is:
  1. HTTP client with 3-step async flow (submit -> poll -> fetch)
  2. JSON parsing of a well-documented API response
  3. Minor model enhancement (declination field)
  4. Terrain painter real-data path
  5. Loading UX on home screen

  The most complex part is the polling loop and ensuring tests cover timeout/failure scenarios without real delays. The wind API client provides a direct pattern to follow.

## Open Questions

- [x] Q1: Should we add `declination` to `HorizonProfile` now or defer to P2B-004?
  - Resolution: Add it now. SPEC-003 explicitly mentions storing it. It is needed for compass correction in P2B-004, and adding it now is trivial (optional Freezed field with default). Adding it later would require another build_runner run and potentially break cached JSON.

- [x] Q2: Should we add `panoramaId` to `HorizonProfile`?
  - Resolution: Yes, add it as an optional field. It enables re-fetching or checking specific panoramas later without resubmitting. The ROADMAP P2B-002 section lists it as a field. Low cost, potential future value.

- [x] Q3: Should the `HomeTerrainPainter` switch from hardcoded bezier to real data, or show both?
  - Resolution: When profile is non-null, use real data path. When null (loading / fallback), use existing hardcoded bezier. SPEC-003 is explicit: "Procedural silhouette stays visible while loading."

- [x] Q4: Should we add disk cache persistence wiring (SharedPreferences integration)?
  - Resolution: Not in this feature. `CachedHorizonProvider` already has `saveToDiskJson()` / `loadFromDiskJson()` methods. The actual disk persistence (calling SharedPreferences) can be wired in a future step or as a small follow-up. Memory cache is sufficient for MVP -- the 2-minute recomputation only happens on cold start without cache.

- [x] Q5: Does the `HorizonProvider.getHorizon()` interface need to change to support the long-running async nature of the HWT call?
  - Resolution: No. The interface already returns `Future<HorizonProfile>`, which handles long-running operations. The `horizonProfileProvider` is an `AsyncValue<HorizonProfile>`, which naturally shows loading state. The 2-minute wait is handled inside the provider's future -- consumers see `AsyncLoading` then `AsyncData`.

- [x] Q6: Should the `HomeTerrainSection` become a `ConsumerWidget` to watch `horizonProfileProvider`?
  - Resolution: Yes. Currently it is a plain `StatefulWidget`. To display real terrain data, it needs to watch `horizonProfileProvider` via Riverpod. The `HomeTerrainPainter` already accepts a `profile` parameter but it is never passed a real profile. The section or its parent needs to read the provider and pass it down.

- [x] Q7: What about the loading indicator ("Computing terrain..." text)?
  - Resolution: Implement as specified in SPEC-003. Small, subtle text below the wind row or at the bottom of the terrain section. Shows only when `horizonProfileProvider` is in loading state. Disappears when data arrives or on error (silent fallback).

- [x] Q8: Should `HwtHorizonProvider` have a `dispose()` method to close the HTTP client?
  - Resolution: Yes, following the `WindApiClient` pattern. The provider in `service_providers.dart` should register `ref.onDispose()` to close the client. This prevents connection leaks.

## Recommended Approach

### Implementation Strategy

Follow the SPEC-003 spec closely. The architecture is already built -- this is a plug-in implementation. The key steps are:

1. **Add declination + panoramaId to HorizonProfile model** -- Minor Freezed model enhancement with optional fields and defaults. Requires build_runner regeneration.

2. **Create HwtHorizonProvider** -- New file implementing the 3-step API flow (submit, poll, fetch). Follow `WindApiClient` patterns for HTTP client injection, error handling, and graceful degradation.

3. **Create HWT API constants** -- URL/timeout constants in a separate file (same pattern as `wind_api_constants.dart`).

4. **Wire into service_providers.dart** -- Replace `MockHorizonProvider()` with `CachedHorizonProvider(delegate: HwtHorizonProvider())`. Register dispose callback.

5. **Update HomeTerrainSection/Painter** -- Make it a ConsumerWidget (or pass profile from parent), add `_buildProfilePath()` for real data, add loading indicator.

6. **Write tests** -- 7-10 tests using `MockClient` covering all API steps, error cases, and parsing.

### Suggested Order of Implementation

1. **Model enhancement** -- Add `declination` and `panoramaId` to `HorizonProfile`, run build_runner
2. **Constants + provider** -- `HwtApiConstants` + `HwtHorizonProvider` (core API client)
3. **Tests** -- `hwt_horizon_provider_test.dart` with mock HTTP client
4. **Wire up** -- Change `service_providers.dart`
5. **Home screen UI** -- Real terrain path in `HomeTerrainPainter`, loading indicator, ConsumerWidget conversion
6. **Home screen tests** -- Verify painter handles real profile, loading state shown

### What to Defer (Not MVP Critical)
- **Disk cache persistence wiring** -- Memory cache is sufficient; SharedPreferences integration can follow
- **AR view terrain masking** -- That is P2B-004+005, not this feature
- **Declination-based compass correction** -- Store the value now, use it in P2B-004
- **Moving average smoothing for terrain path** -- Only add if real data looks jagged on device
- **Pre-computing panoramas for common locations** -- Future optimization
