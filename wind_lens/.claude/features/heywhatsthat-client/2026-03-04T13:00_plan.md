## Architecture Overview

This feature replaces `MockHorizonProvider` with a real `HwtHorizonProvider` that calls the HeyWhatsThat API to fetch terrain horizon profiles. The existing architecture (SPEC-001) was designed specifically for this plug-in -- the interface, model, cache decorator, and provider swap-point are all already built.

### Data Flow

```
GPS Fix (effectivePositionProvider)
    |
    v
horizonProfileProvider (AsyncValue<HorizonProfile>)
    |
    v
horizonProviderServiceProvider
    |
    v
CachedHorizonProvider (memory + disk cache, 3-decimal key)
    |  cache miss?
    v
HwtHorizonProvider (implements HorizonProvider)
    |
    |--- Step 1: Submit panorama request (query.cgi)
    |       Response: "PANORAMA_ID queued lat lon ..."
    |       Parse: body.trim().split(' ')[0]  <-- CORRECTED from spec
    |
    |--- Step 2: Poll until ready (results/{id}/data)
    |       Not ready: body starts with "running"
    |       Ready: body starts with "ok"
    |       Timeout: 5 minutes, 10-second intervals
    |
    |--- Step 3: Fetch result (result.json?id={id})
    |       Parse: limits[360] -> elevationAngles
    |       Extract: declination (integer)
    |       Guard: empty body = invalid ID (HTTP 200, X-App-Status: 460)
    |
    v
HorizonProfile (Freezed model)
  - latitude, longitude
  - elevationAngles: Map<double, double> (360 entries)
  - declination: double (NEW, default 0.0)
  - panoramaId: String? (NEW, optional)
  - fetchedAt: DateTime
    |
    v
HomeTerrainSection (ConsumerWidget)
    |--- profile != null? --> _buildProfilePath() from real elevation data
    |--- profile == null? --> existing procedural bezier path
    |
    v
HomeTerrainPainter (CustomPainter)
  - Terrain fill, ridge glow, horizon line (unchanged)
  - Path source switches between procedural and real data
```

### HwtHorizonProvider

Key design decisions:

1. **Interface match:** Uses named parameters `{required double latitude, required double longitude}` to match `HorizonProvider` interface (SPEC-003 code examples used positional -- those are wrong).

2. **HTTP client injection:** Constructor accepts optional `http.Client` for testability, same pattern as `WindApiClient`.

3. **Polling loop testability:** The polling delay is controlled by an injectable `Duration` parameter (default 10 seconds). Tests pass `Duration.zero` for instant polling. This avoids needing to mock `Future.delayed`.

4. **Graceful degradation:** Any exception in the 3-step flow is caught at the top level, returning `HorizonProfile.flat()`. Never throws to caller.

5. **Empty body guard:** `result.json` returns HTTP 200 with empty body for invalid IDs. Must check `response.body.isNotEmpty` before `jsonDecode`.

6. **Dispose pattern:** `dispose()` method closes the HTTP client. Provider registers `ref.onDispose()`.

```dart
class HwtHorizonProvider implements HorizonProvider {
  final http.Client _client;
  final Duration _pollInterval;

  HwtHorizonProvider({
    http.Client? client,
    Duration pollInterval = const Duration(seconds: 10),
  }) : _client = client ?? http.Client(),
       _pollInterval = pollInterval;

  @override
  Future<HorizonProfile> getHorizon({
    required double latitude,
    required double longitude,
  }) async { ... }

  Future<String> _submitPanorama(double lat, double lng) async { ... }
  Future<void> _waitForCompletion(String id) async { ... }
  Future<HorizonProfile> _fetchProfile(String id, double lat, double lng) async { ... }
  void dispose() { _client.close(); }
}
```

## Implementation Notes

### Design Decisions

1. **HomeTerrainSection as ConsumerStatefulWidget (not passing profile from HomeScreen)**
   - Rationale: HomeTerrainSection already owns particle state in `_HomeTerrainSectionState`. Making it a `ConsumerStatefulWidget` keeps the Riverpod watch co-located with the widget that uses it. HomeScreen does not need to know about horizon profiles.
   - Alternative considered: Pass profile from HomeScreen. Rejected because it would require HomeScreen to watch horizonProfileProvider and add a parameter, creating unnecessary coupling.

2. **Injectable poll interval for testing**
   - The polling loop uses `Future.delayed(_pollInterval)`. Tests inject `Duration.zero` to avoid real delays.
   - Alternative considered: Inject a `Stopwatch` or `Clock`. Rejected as over-engineered for this use case.

3. **Declination stored on HorizonProfile, not used yet**
   - Declination is extracted from the API response and stored on the model. It is NOT applied to compass bearing lookups in this feature. That happens in P2B-004 (terrain sky mask) when the profile is used for AR view masking.
   - This avoids coupling the home screen terrain painter to compass correction logic.

4. **No disk cache wiring in this feature**
   - `CachedHorizonProvider` already has `saveToDiskJson()` / `loadFromDiskJson()` methods. Wiring to SharedPreferences is deferred. Memory cache is sufficient -- the API call takes 5-15 seconds (not 2 minutes as spec claimed), and cold starts are infrequent.

5. **Loading indicator as positioned text, not a spinner**
   - SPEC-003 specifies subtle text ("Computing terrain...") in DM Mono, grey (#444). No spinner widget. This matches the app's dark, minimal aesthetic.
   - Shows only during `AsyncLoading` state. Disappears on success (immediate) or error (silent fallback).
   - No "Terrain loaded" toast -- SPEC-003 suggests one that fades after 3 seconds, but this adds animation complexity for minimal user value. Deferred.

### Patterns Used

- **HTTP client injection** -- same as `WindApiClient`
- **Graceful degradation** -- same as wind API (flat fallback, never crash)
- **Constants class** -- same as `WindApiConstants`
- **Provider swap-point** -- one `return` statement change
- **Dispose via ref.onDispose()** -- same as windDataSource provider

### Trade-offs

| Decision | Pro | Con |
|----------|-----|-----|
| Injectable pollInterval vs clock injection | Simple, test-friendly | Less precise timing control |
| ConsumerStatefulWidget vs passing from parent | Encapsulated, self-contained | Another ConsumerWidget in tree |
| Store declination now, use later | One model change, not two | Unused field for now |
| No disk cache wiring | Smaller scope, faster delivery | Cold start re-fetches every time |
