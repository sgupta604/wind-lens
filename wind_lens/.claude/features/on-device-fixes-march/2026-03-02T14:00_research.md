## BUG A: Dome Wind Speed Mismatch (0.5 m/s dome vs 2.7 m/s AR)

### Root Cause Analysis

**The dome and AR view fetch wind data through completely different code paths:**

| Aspect | AR View | Dome View |
|--------|---------|-----------|
| Provider | `windDataProvider` (data_providers.dart) | `domeWindProfileProvider` -> `DomeWindFetcher` |
| Source class | `OgcEdrWindDataSource` -> `CachedWindDataSource` | `DomeWindFetcher` -> `WindApiClient` directly |
| API method | `WindApiClient.fetchPointWind()` | `WindApiClient.fetchPointWindSeries()` |
| Time param | `_nearestHourUtc()` (single timestamp) | `_dateTimeRangeUtc(72)` (72-hour range) |
| What is shown | `WindData.speed` at selected altitude | `_surfaceSpeed(windField)` from `DomeWindField.layers.first` |

**Likely cause: Time alignment mismatch.**

`fetchPointWind()` uses `_nearestHourUtc()` which rounds to the nearest hour UTC. `fetchPointWindSeries()` uses `_dateTimeRangeUtc(72)` which also starts at the nearest hour, so the first timestep SHOULD be the same. However:

1. The dome info bar calls `_surfaceSpeed(windField)` which reads `field.layers.first`. If the layers are sorted by altitude ascending, `layers.first` is the surface (10m) layer -- this is correct.

2. The DomeWindFetcher uses `fetchPointWindSeries` with `pressureLevel: 0` for surface, which is the same surface collection as the AR view. So the API endpoint is the same.

3. **KEY DIFFERENCE: The Shyft time-series response returns an array of values for the requested time range.** The `_parseShyftTimeSeriesResponse` method processes the CoverageCollection and returns timestamped u/v arrays. The `_parseShyftPositionResponse` method (used by `fetchPointWind`) reads a single Coverage.

4. **POTENTIAL ISSUE: The time series may use different GFS model cycles than the point query.** If the time range starts at the nearest hour but the GFS data available starts at a different initialization time, hour 0 of the time series may not match the single-point "nearest hour" query.

5. **ANOTHER POTENTIAL ISSUE: Caching.** The dome has its own static cache (`DomeWindFetcher._cached` with key `dome_lat_lng`). The AR has `CachedWindDataSource` with key `lat_lng_altitude`. If one is cached from an earlier model run and the other is fresh, they could differ.

6. **MOST LIKELY CAUSE: The `fetchPointWindSeries` may be getting Shyft data from a different forecast initialization time.** The `_dateTimeRangeUtc(72)` creates a range from now to +72h. The API may return data from the latest available model run, whose hour-0 analysis could differ from what `_nearestHourUtc()` returns for a single point query.

**RECOMMENDATION:** The dome view should use the SAME `fetchPointWind()` method for the "live" (hour 0) case to ensure consistency, OR both views should use the same underlying data path. The simplest fix: verify the dome's hour-0 wind field matches the AR's wind, potentially by using the same `WindApiClient` instance and ensuring the same time parameter.

**Alternative (simpler) investigation:** Add debug logging to both paths to see exactly what u/v values are returned. The mismatch could be as simple as a different GFS model init time.

### Files Involved
- `/workspace/wind_lens/lib/services/wind/dome_wind_fetcher.dart` (dome's fetch path)
- `/workspace/wind_lens/lib/services/wind/ogc_edr_wind_source.dart` (AR's fetch path)
- `/workspace/wind_lens/lib/services/wind/wind_api_client.dart` (shared API client, different methods)
- `/workspace/wind_lens/lib/features/wind_dome/widgets/dome_info_bar.dart` (dome speed display)
- `/workspace/wind_lens/lib/features/wind_dome/providers/dome_providers.dart` (dome provider graph)

### Recommended Fix
The most reliable fix: make the DomeInfoBar display the wind speed from the same provider the AR view uses when showing "Live" data (hoursAhead == 0). For forecast hours, the dome's own time-series data is the only option.

Alternatively, confirm both paths return the same u/v for the same time and location. If they differ due to API behavior, align the datetime parameters.

## BUG B: Forecast Slider Not Updating Dome Particles

### Root Cause Analysis

**Provider chain:**
1. `hoursAheadProvider` (StateProvider<int>, default 0)
2. `currentDomeWindFieldProvider` watches `domeWindProfileProvider` and `hoursAheadProvider`
3. Calls `profile.fieldAt(hours)` to select the hour's DomeWindField

**The tick loop reads:**
```dart
final field = ref.read(currentDomeWindFieldProvider);
```

**THIS IS THE BUG.** The tick loop uses `ref.read()` which reads the value ONCE. The Ticker callback runs outside of the build cycle. When `hoursAheadProvider` changes, `currentDomeWindFieldProvider` is updated (because it watches `hoursAheadProvider`), and `ref.watch(currentDomeWindFieldProvider)` in a widget build would see the new value. But the tick loop uses `ref.read()` in a `Ticker` callback.

However, `ref.read()` actually does read the current value at the time of the call -- it doesn't cache. `currentDomeWindFieldProvider` is a `Provider<DomeWindField?>` (synchronous computed provider) that watches `hoursAheadProvider`. When the slider changes `hoursAheadProvider`, the `currentDomeWindFieldProvider` is invalidated and recomputed.

**Wait -- `ref.read()` on a synchronous `Provider` DOES return the current computed value.** So if `hoursAheadProvider` changes, `currentDomeWindFieldProvider` should recompute and `ref.read()` in the next tick should see the new value.

**Let me re-examine.** The `currentDomeWindFieldProvider` is:
```dart
final currentDomeWindFieldProvider = Provider<DomeWindField?>((ref) {
  final profile = ref.watch(domeWindProfileProvider).valueOrNull;
  if (profile == null) return null;
  final hours = ref.watch(hoursAheadProvider);
  return profile.fieldAt(hours);
});
```

This is a Riverpod `Provider` (not `FutureProvider`). It watches `hoursAheadProvider`. When the slider updates `hoursAheadProvider`, this provider gets invalidated and recomputed. The tick loop's `ref.read(currentDomeWindFieldProvider)` in the NEXT tick will get the new value.

**So the provider chain should work correctly.** The slider updates `hoursAheadProvider`, which invalidates `currentDomeWindFieldProvider`, which recomputes with the new hour, and the tick loop reads the new field on the next frame.

**POSSIBLE REAL ISSUE: The wind field profile might have identical data across hours.** If the GFS time-series query returned the same u/v for all forecast hours (e.g., if the API returned only one timestep but `DomeWindFetcher` padded the rest with the same values), then changing hours wouldn't visually change anything.

**ANOTHER POSSIBILITY: The DomeWindProfile has only 1 entry.** If `fetchPointWindSeries` returns only 1 timestep (e.g., if the Shyft API interprets the datetime range differently), then `profile.fieldAt(any_hour)` would always return `hourly[0]` due to clamping.

**MOST LIKELY CAUSE:** Verify the time-series response actually returns 72+ distinct timesteps with varying u/v values. If it returns only a few timesteps, the slider would appear to have no effect.

### Files Involved
- `/workspace/wind_lens/lib/features/wind_dome/widgets/dome_forecast_slider.dart` (slider UI)
- `/workspace/wind_lens/lib/features/wind_dome/wind_dome_screen.dart` (line 109: `ref.read(currentDomeWindFieldProvider)`)
- `/workspace/wind_lens/lib/features/wind_dome/providers/dome_providers.dart` (provider chain)
- `/workspace/wind_lens/lib/services/wind/dome_wind_fetcher.dart` (fetch + assemble)
- `/workspace/wind_lens/lib/services/wind/wind_api_client.dart` (`fetchPointWindSeries` + parsing)

### Recommended Fix
1. Add debug logging to `DomeWindFetcher.fetch()` to print the number of timesteps returned and whether u/v values vary across hours.
2. If the API is returning fewer than 72 timesteps, the current code already handles this (padding with zeros and clamping in `fieldAt`). But the visual effect would be that the slider stops having any effect past the last real timestep.
3. If the slider IS working but the changes are too subtle to notice visually, add an on-screen indicator of the current field's u/v (already partially done via DomeInfoBar).

**Note:** This bug may be "works correctly but user didn't notice the change" if the wind forecast doesn't vary much over the next 72 hours at that location. Or it could be a genuine data pipeline issue.

## BUG C: Jet Stream Altitude Shows 0.0 m/s in AR

### Root Cause Analysis

**AR wind data flow:**
1. User selects `AltitudeLevel.jetStream` via altitude slider
2. `selectedAltitudeProvider` updates -> `windDataProvider` refetches
3. `windDataProvider` calls `source.getWind(position, altitude: jetStream)`
4. `OgcEdrWindDataSource._altitudeToPressure(jetStream)` returns **300** (hPa)
5. `WindApiClient.fetchPointWind(pressureLevel: 300)` is called

**Shyft path (primary):**
- Collection: `GFS_isobaric` (has 300 hPa per constants doc: "850, 700, 500, **300**, 200, 100, 70, 20, 10 hPa")
- Query: `z=300`
- This SHOULD work.

**Folkweather fallback path:**
- `_folkCollection(300)`: 300 is NOT in `folkHrrrLevels` ({850, 925, 1000}), so it routes to `folkGfsIsobaricCollection` ("gfs-isobaric-latest")
- GFS isobaric available levels: "10, 20, 70, 100, 200, **300**, 500, 700, 1000 hPa"
- This SHOULD also work.

**POSSIBLE CAUSES:**

1. **Shyft 300 hPa actually returns empty/zero data.** The constants say 300 hPa is available, but it might return null/zero wind at that level for the queried location/time. If Shyft returns 0,0 that's a valid response (no fallback triggered since it's not an HTTP error).

2. **Shyft returns an HTTP error at 300 hPa -> falls to Folkweather -> Folkweather also fails.** Both fail: `fetchPointWind` returns `(0.0, 0.0, 'none')`.

3. **CLAUDE.md says jet stream is 250 hPa** in the altitude level table, but `OgcEdrWindDataSource` uses 300 hPa. The table says:
   - "Jet Stream | 10,500m | Purple | ~50 m/s | **250 hPa** | 0.3"
   But the code maps jetStream to 300 hPa.

   **THIS IS SUSPICIOUS.** 250 hPa is the standard jet stream level. The code uses 300 hPa instead. Could the original developer have used 300 hPa intentionally (because it's more widely available), or is this a bug?

   Looking at the available levels:
   - Shyft GFS isobaric: 850, 700, 500, **300**, 200, 100, 70, 20, 10 hPa -- NO 250 hPa!
   - Folkweather HRRR isobaric: 1000, 925, 850, 700, 500, 300, **250** hPa -- HAS 250 hPa!
   - Folkweather GFS isobaric: 10, 20, 70, 100, 200, **300**, 500, 700, 1000 hPa -- NO 250 hPa!

   So **Shyft doesn't have 250 hPa**, and Folkweather GFS doesn't have it either. Only HRRR has 250 hPa. Using 300 hPa was likely intentional because it's available on both APIs.

4. **The real question: does Shyft actually return data at 300 hPa?** The comment says it's available, but GFS 300 hPa might not have data at all times/locations.

5. **Most likely: the Shyft API is returning an error for 300 hPa (possibly because the nearest-hour GFS run doesn't have that level initialized yet), and Folkweather GFS fallback at 300 hPa also fails, resulting in (0.0, 0.0, 'none').** This would explain why surface and mid-level work (they're well-established API endpoints) but jet stream doesn't.

### Files Involved
- `/workspace/wind_lens/lib/services/wind/ogc_edr_wind_source.dart` (pressure mapping: jetStream -> 300)
- `/workspace/wind_lens/lib/services/wind/wind_api_client.dart` (`fetchPointWind` + Shyft/Folkweather fallback)
- `/workspace/wind_lens/lib/services/wind/wind_api_constants.dart` (available pressure levels)
- `/workspace/wind_lens/lib/core/providers/data_providers.dart` (windDataProvider triggers fetch)

### Recommended Fix
1. **Test the API directly** by calling Shyft at 300 hPa and checking the response. If it consistently returns errors or zeros, try 200 hPa instead (which is available on both Shyft and Folkweather GFS).
2. **Improve logging** in `fetchPointWind` to capture which API succeeded/failed and what data was returned.
3. If 300 hPa genuinely doesn't work, change the jet stream mapping to **200 hPa** (both Shyft and Folkweather GFS have it). 200 hPa is approximately 11,800m, which is closer to the documented 10,500m jet stream altitude.
4. Alternatively, try Folkweather HRRR at 250 hPa as the primary for jet stream, with Shyft 300 hPa or 200 hPa as fallback.

## BUG D: Location Display on AR Screen

### Analysis

**Current state:**
- `LocationIndicatorChip` exists at `/workspace/wind_lens/lib/features/wind_dome/widgets/location_indicator_chip.dart`
- It is used in `WindDomeScreen` (positioned below the info bar)
- It reads `locationOverrideProvider` and `effectivePositionProvider`
- It is a `ConsumerWidget` with no dome-specific logic

**Problem:** The chip is in the dome's widget directory (`features/wind_dome/widgets/`). To use it in the AR view, it either needs to:
1. Move to a shared location (e.g., `lib/core/widgets/` or a new `lib/shared/widgets/`)
2. Stay where it is and the AR view imports it from the dome widget path

**Option 2 is simpler** since the widget has zero dome-specific logic. It reads from `core/providers/location_override_provider.dart` which is already shared. However, it's architecturally cleaner to move it to a shared location.

**Where to place it in AR view:**
Looking at `ARViewScreen`, the existing layers are:
- Layer 1: CameraView
- Layer 2: ParticleOverlay
- Layer 3: DebugPanel (top-left)
- Layer 5: AltitudeSlider (right center)
- Layer 6: InfoBar (bottom-left)
- Layer 7: CompassWidget (above InfoBar)
- Layer 8: DataStatusBar (top center)

The chip should go below the DebugPanel toggle button area or near the DataStatusBar. The dome places it at `top + 56` which is below the info bar. In the AR view, it could go at the top-right or below the DataStatusBar.

### Files Involved
- `/workspace/wind_lens/lib/features/wind_dome/widgets/location_indicator_chip.dart` (existing widget)
- `/workspace/wind_lens/lib/features/ar_view/ar_view_screen.dart` (where to add it)

### Recommended Fix
1. Move `LocationIndicatorChip` from `features/wind_dome/widgets/` to a shared location (e.g., `lib/shared/widgets/location_indicator_chip.dart` or keep it where it is and import cross-feature).
2. Add it as a new `Positioned` widget in ARViewScreen's Stack.
3. Position it near the top of the screen, possibly at `top + safeArea + 48` on the right side, to avoid overlapping with the DebugPanel on the left.

## Recommended Approach

### Implementation Strategy

**BUG A (Dome wind speed mismatch):**
- Add debug logging to both `fetchPointWind` and `fetchPointWindSeries` to compare their surface u/v returns.
- If the values genuinely differ, the cleanest fix is to ensure the dome uses the same data as the AR for "Live" mode. Options:
  1. Have the dome also use `fetchPointWind` for hour 0 and only use the time-series for forecast hours.
  2. Have the AR also use the time-series data (most consistent, but more complex).
  3. Accept the difference and document it (least preferred).
- Simplest fix: In `DomeInfoBar`, when `hoursAhead == 0`, read the wind from the same provider as the AR view (`windDataProvider`) instead of from the dome's own data.

**BUG B (Forecast slider not updating):**
- Add debug logging to `DomeWindProfile` to verify: (a) how many hourly entries exist, (b) whether u/v values differ across hours.
- If the time-series response genuinely has 72 distinct entries with varying wind, the slider should work because `ref.read(currentDomeWindFieldProvider)` reads the latest value.
- If the issue is that the API returns fewer entries (or all-same values), that's an API/data issue, not a code bug.

**BUG C (Jet stream 0.0 m/s):**
- Test the Shyft API at 300 hPa live. If it consistently fails or returns zero, change the jet stream mapping from 300 hPa to 200 hPa.
- Consider adding a special fallback path: try 300 hPa on Shyft first, if that fails try 250 hPa on Folkweather HRRR, then 200 hPa on GFS.
- The simplest fix that's most likely to work: map jetStream to 200 hPa (available on both Shyft and Folkweather GFS).

**BUG D (Location display on AR):**
- Move `LocationIndicatorChip` to a shared location.
- Add it to `ARViewScreen` as a Positioned widget in the Stack.
- Update the dome import to use the new shared path.

### Order of Work
1. **BUG D** (simplest, UI only, no data investigation needed)
2. **BUG C** (clear fix path: change pressure level mapping)
3. **BUG A** (needs data investigation, may be a simple parameter fix)
4. **BUG B** (may be a non-issue once BUG A is fixed; needs debugging)

### What to Defer (Not MVP Critical)
- Aligning the dome and AR wind data paths to use a single source of truth (complex, can be done post-MVP)
- Adding a "wind data source" indicator to the UI (which API was used)
- 250 hPa HRRR routing for jet stream (200 hPa on GFS is sufficient)

double _surfaceSpeed(DomeWindField? field) {

  final surface = field.layers.first;
  return sqrt(surface.u * surface.u + surface.v * surface.v);
}
