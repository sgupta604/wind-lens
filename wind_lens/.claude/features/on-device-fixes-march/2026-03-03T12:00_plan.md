### BUG D: Location Display on AR Screen

**Approach:** Move `LocationIndicatorChip` from `features/wind_dome/widgets/` to `core/widgets/` (canonical shared location per project architecture). Leave a re-export shim at the old path so the dome import does not break. Add the widget to `ARViewScreen`'s Stack.

**Widget placement in AR screen:**
- Position: top-left, below the DataStatusBar area, next to DebugPanel toggle

### BUG C: Jet Stream 0.0 m/s

**Approach:** Change the pressure level mapping in `OgcEdrWindDataSource._altitudeToPressure()` from 300 hPa to 200 hPa.

**Justification:**
- 200 hPa is available on BOTH Shyft GFS_isobaric and Folkweather gfs-isobaric-latest
- 200 hPa ~ 11,800m altitude, which is closer to the documented jet stream altitude (10,500m) than 300 hPa (~9,000m)
- CLAUDE.md altitude table already says 250 hPa for jet stream; 200 hPa is the nearest available level
- 300 hPa may be returning empty/error data from Shyft, causing the 0.0 m/s display

**Dome impact:** The dome does NOT fetch jet stream data (it only fetches surface/850/700 hPa), so this change affects only the AR view.

**Update OgcEdrWindDataSource doc comment:** Change "300 hPa (~9,000m)" to "200 hPa (~11,800m)".

### BUG A: Dome Wind Speed Mismatch

**Approach:** Make `DomeInfoBar` display the AR view's wind speed when in "Live" mode (hoursAhead == 0). For forecast hours (hoursAhead > 0), continue using the dome's own time-series data.

**Implementation:**
1. `DomeInfoBar` becomes a `ConsumerWidget` that also watches `windDataProvider` (it already is a ConsumerWidget)
2. When `hoursAhead == 0`: display speed from `windDataProvider.valueOrNull?.speed ?? _surfaceSpeed(windField)`
3. When `hoursAhead > 0`: display `_surfaceSpeed(windField)` as before

**Why this works:**
- `windDataProvider` is the same provider the AR view reads, ensuring identical values
- `windDataProvider` watches `effectivePositionProvider` and `selectedAltitudeProvider`, so it auto-updates on location/altitude changes
- The dome's own time-series data from `DomeWindFetcher` may use a different GFS model initialization than the point query, causing the mismatch
- For forecast hours, only the dome's time-series has future data, so we must use it

**Fallback:** If `windDataProvider` is still loading (AsyncValue.loading), fall back to the dome's surface speed so the UI is never blank.

### BUG B: Forecast Slider Not Updating Dome Particles

**Root cause analysis conclusion:** The provider chain (`hoursAheadProvider` -> `currentDomeWindFieldProvider` -> tick loop `ref.read()`) is architecturally correct. `ref.read()` on a synchronous `Provider` returns the current computed value at the time of each tick.

**Most likely cause:** The time-series API response has insufficient distinct timesteps, OR wind values do not change noticeably across hours at the test location. This is a data quality issue, not a code bug.

**Approach:**
1. Add lightweight debug logging to `DomeWindFetcher.fetch()` to print the number of timesteps returned and whether u/v values vary across hours
2. After fixing BUG A (which aligns live data), re-test the slider on device
3. If the slider still appears non-functional, the logging will reveal whether the time-series has distinct data

**No code changes to provider chain or tick loop.** The architecture is correct.

## Implementation Notes

### Decisions

1. **200 hPa over 250 hPa for jet stream:** 250 hPa is only available on Folkweather HRRR (CONUS-only, 3km). 200 hPa is available on both Shyft GFS and Folkweather GFS (global coverage). 200 hPa is closer to the jet stream core (~11,800m vs 10,500m documented).

2. **Re-export shim for LocationIndicatorChip:** Following the project pattern (see `lib/models/`, `lib/widgets/`, etc.), leave a single-line re-export at the old path. This prevents breaking the dome import. The dome's `wind_dome_screen.dart` can optionally be updated to import from the new path.

3. **windDataProvider in DomeInfoBar:** We add a direct watch on `windDataProvider` only in `DomeInfoBar`, not in the tick loop or dome painter. This is a display-only change that does not affect rendering performance.

4. **No DomeWindFetcher changes for BUG A:** The fetcher continues to work as-is for forecast data. Only the display in DomeInfoBar is changed for the live case.

### Patterns Used

- **Re-export shim** (established pattern for directory restructure)
- **ConsumerWidget with ref.watch** (standard Riverpod pattern)
- **Positioned widget in Stack** (established AR screen layer pattern)
- **Graceful fallback** (windDataProvider loading -> fall back to dome data)

### Trade-offs

- **BUG A fix is display-only:** The dome's time-series data at hour 0 may still differ from the AR point query. We choose to display the AR value for consistency rather than fixing the API alignment (which would be complex and potentially break forecast data).
- **BUG B may be a non-issue:** If debug logging reveals the time-series has valid varying data, the "bug" is that wind doesn't change much at the test location. We accept this as expected behavior.
