# Plan: Sky Detection Cloud Coverage Fix (BUG-011)

## Metadata

- **Feature:** sky-detection-clouds
- **Timestamp:** 2026-02-06
- **Status:** planned
- **Based On:** `.claude/active-work/sky-detection-clouds/diagnosis.md`
- **Bug ID:** BUG-011
- **Severity:** Medium

## Problem Summary

The HSV histogram's `matchScore()` hard-rejects white cloud pixels because they have
near-zero saturation (0.01-0.10) and achromatic hue (0), while the blue-sky profile
expects saturation 0.30-0.45 and hue 200-220. Result: clouds get score 0.0 and are
excluded from the sky mask, reducing reported sky fraction from an expected 60-80%
down to 29-35% on days with clouds.

## Architecture Overview

This is a targeted scoring fix, not a sky detection rewrite. The change adds a
secondary cloud detection path in `_generateMask()` that runs alongside the existing
histogram-based blue-sky scoring.

```
Before:
  pixel HSV --> matchScore(hsv) --> colorScore --> * positionWeight --> threshold

After:
  pixel HSV --+--> matchScore(hsv) ---------> blueScore -+
              |                                          |
              +--> _isCloudLike(hsv) --> cloudScore -----+--> max() --> colorScore
                                                               |
                                                         * positionWeight --> threshold
```

The dual-path approach means:
- Blue sky pixels still go through the existing histogram scoring (unchanged)
- Cloud/bright pixels get a dedicated score based on desaturation and brightness
- The final color score is the MAX of both paths
- Position weight still applies to both, preventing bright ground objects from
  being classified as sky

## Component Architecture

### Change 1: Dual-path scoring in `_generateMask()`

**File:** `auto_calibrating_sky_detector.dart`
**Method:** `_generateMask()`, lines 464-466

Current code:
```dart
final colorScore = _skyHistogram!.matchScore(hsv);
final combinedScore = colorScore * positionWeight;
```

New code:
```dart
final blueScore = _skyHistogram!.matchScore(hsv);
final cloudScore = _isCloudLike(hsv) ? _cloudSkyScore(hsv) : 0.0;
final colorScore = blueScore > cloudScore ? blueScore : cloudScore;
final combinedScore = colorScore * positionWeight;
```

### Change 2: Cloud detection helper `_isCloudLike()`

**File:** `auto_calibrating_sky_detector.dart`
**Location:** New private method

```
_isCloudLike(HSV hsv) -> bool
  Returns true when:
  - Saturation < 0.15 (achromatic / very desaturated)
  - Value >= 0.45 (bright enough to be sky, not a dark shadow)
```

This intentionally uses generous thresholds. The position weight provides
additional filtering against false positives at the bottom of the frame
(e.g., white walls, concrete). A white object at y=0.7 would get
positionWeight ~0.20, making combinedScore = 0.88 * 0.20 = 0.18, which
is below the 0.4 detection threshold.

### Change 3: Cloud scoring function `_cloudSkyScore()`

**File:** `auto_calibrating_sky_detector.dart`
**Location:** New private method

```
_cloudSkyScore(HSV hsv) -> double (0.0 to 1.0)
  brightnessScore = ((V - 0.45) / 0.55).clamp(0, 1)
  desaturationScore = (1.0 - S / 0.15).clamp(0, 1)
  return (brightnessScore * 0.6 + desaturationScore * 0.4).clamp(0, 1)
```

Scoring rationale:
- Brightness is weighted 60% because bright pixels are more likely to be sky/cloud
- Desaturation is weighted 40% because lower saturation = more cloud-like
- At S=0.02, V=0.96 (white cloud): score = (0.93 * 0.6 + 0.87 * 0.4) = 0.91
- At S=0.08, V=0.75 (gray cloud): score = (0.55 * 0.6 + 0.47 * 0.4) = 0.52
- At S=0.05, V=0.25 (dark shadow): V < 0.45, so _isCloudLike returns false

### Change 4: Widen `isSkyLikeColor()` threshold

**File:** `hsv_histogram.dart`
**Method:** `isSkyLikeColor()`, line 38

Change saturation threshold from 0.15 to 0.20 for the gray/overcast path.
This allows clouds with a slight blue tint (S=0.15-0.20) to be included
during calibration sampling. Low risk because colors with S > 0.20 still
go through the blue hue check (180-250).

## Implementation Notes

### Why `_generateMask()` instead of `matchScore()`

The diagnosis suggests either location. We choose `_generateMask()` because:
1. `matchScore()` is a pure color-matching function on `HSVHistogram` -- it should
   only know about the histogram profile it was built from
2. Cloud detection is a *separate scoring concept* that doesn't belong in the
   histogram's statistical model
3. Putting it in `_generateMask()` keeps the two scoring paths visually distinct
   and easy to tune independently
4. The histogram remains a reusable component without cloud-specific logic baked in

### Testing approach for private methods

The `_isCloudLike()` and `_cloudSkyScore()` methods are private. To test them, we
will expose them as `@visibleForTesting` public methods (same pattern used for
`getPositionWeight()` and `getSampleRegionBottom()` in the existing code). This
allows direct unit testing without needing to construct CameraImage objects.

### Performance impact

Negligible. The cloud check adds 2 comparisons and potentially 3 arithmetic
operations per pixel. At 128x96 mask resolution = 12,288 pixels, this adds
roughly 0.01ms to frame processing time, well within the 16ms budget.

### False positive mitigation

The position weight is the primary defense against false positives:
- White wall at y=0.5: cloudScore=0.9 * positionWeight=0.46 = 0.41 --> borderline
- White wall at y=0.6: cloudScore=0.9 * positionWeight=0.33 = 0.30 --> rejected
- White cloud at y=0.1: cloudScore=0.9 * positionWeight=0.85 = 0.77 --> accepted

This is acceptable because:
1. Walls are typically in the lower half of the frame when the phone is tilted up
2. At high pitch angles (where calibration happens), clouds ARE at the top
3. The existing position weight already handles this exact scenario for blue sky

## Non-Goals

- **Not changing the histogram algorithm** -- `matchScore()` remains untouched
- **Not adding ML-based cloud detection** -- too complex for this fix
- **Not handling trees/buildings** -- those have saturation > 0.15 and are handled
  by the existing histogram rejection
- **Not adjusting detection threshold** -- 0.4 remains appropriate
- **Not changing calibration logic** -- the `isSkyLikeColor()` threshold tweak is
  the only calibration-related change

## Risk Assessment

**Low risk.** The change is additive:
- Existing blue sky scoring is completely unchanged
- Cloud scoring is a MAX with the existing score, so it can only increase coverage
- Position weight still applies, maintaining ground rejection
- If cloud scoring causes issues, the two helper methods can be disabled with a
  single `false &&` guard in `_generateMask()`
