### Warnings/Critical Notes from Spec
> fetchWindGrid currently only fetches a single time step (uses _nearestHourUtc(), not _dateTimeRangeUtc()). It must be extended to support time-series for 72-hour forecast compatibility.

> Shyft GFS_isobaric is broken for <=300 hPa -- returns HTTP 500. Only 500, 700, 850 work. This is already handled by the fallback pattern but affects available data.

> HRRR is CONUS-only. Outside the continental US, only GFS data is available (25km resolution). At 15km dome radius, GFS provides ~1-2 grid points. At 50km, ~4-8 grid points.

> Area queries near coastlines or data boundaries can return nulls/zeros for some grid points (noted in data-resolution-audit.md).

## Constraints

### Performance
- `DomeWindField.sample()` called 2000 * 60 = 120,000 times/second
- Bilinear interpolation is 4 multiplications + 4 additions per component = ~16 FLOPs -- negligible
- The `WindField.interpolateAtCoord()` method already exists and is efficient
- Coordinate conversion (render-space to lat/lng) adds ~4 multiplications per call
- Total overhead: ~30-40 FLOPs per sample call -- well under 1 microsecond on modern mobile

### API / Network
- Current: 3 API calls per fetch (3 altitudes x 1 point each, time-series)
- Grid time-series: 3 API calls per fetch (3 altitudes x 1 area each, time-series)
- Area queries return more data per call (grid of u/v values per timestep per altitude)
- Response size: 72 hours x ~10-100 grid points x 2 doubles = ~10-150 KB per altitude
- Folkweather HRRR area queries may return ~100 grid points at 15km radius
- Rate limits: unknown, but we already cache for 10 minutes

## Risk Assessment

### Technical Risks
| Risk | Impact | Likelihood | Mitigation |
|------|--------|------------|------------|
| Area time-series API response format differs from point time-series | High | Medium | Parse both formats; add robust error handling. Test with real API responses before implementing. |
| HRRR area queries slow/timeout for large 50km radius | Medium | Medium | Increase timeout for grid queries. Fetch in background. Show loading state. |
| Grid memory usage at 50km (1000+ points x 72 hours x 3 levels) | Medium | Low | ~50MB worst case. Acceptable on modern phones. Could limit to 24 hours for 50km. |
| Bilinear interpolation edge artifacts near coastlines (null grid points) | Low | Medium | WindField already handles null->0.0. Edge particles will get slightly wrong wind -- acceptable. |
| OGC EDR area endpoint does NOT support datetime ranges | High | Medium | If true, would need to make 72 separate area queries per altitude -- likely too many. Fallback: only use grid for live/current hour, point data for forecast hours. |
| Performance regression in hot path | Medium | Low | Benchmark before/after. WindField.interpolateAtCoord is simple math. |

### Complexity
- **Level:** Medium
- **Rationale:** The infrastructure is largely built (fetchWindGrid, WindField, bilinear interpolation). The main complexity is in:
  1. Adding time-series support to area queries (may need API exploration)
  2. Cleanly integrating grid data into the DomeWindField/DomeWindLayer model hierarchy
  3. Coordinate conversion between render-space and geographic coordinates
  4. Handling the fallback between grid and point data gracefully

## Open Questions

- [x] Q1: What dome sizes should trigger grid fetch vs point fetch?
  - Resolution: >= 15km uses grid fetch, < 15km uses point fetch. At 5km radius (10km diameter) HRRR only has ~2-4 grid points, not worth the extra data. At 15km radius (30km diameter), ~55-100 HRRR grid points provide meaningful spatial variation.

- [x] Q2: Should the grid be fetched lazily (only when large preset selected)?
  - Resolution: Yes. Only fetch grid when domeSizeProvider >= 15000. When user switches to smaller preset, the existing point data continues to work. When switching to larger preset, trigger grid fetch (with loading indicator).

- [x] Q3: How to handle the forecast time slider with grid data?
  - Resolution: Two approaches depending on API capability:
  - **If area time-series works:** Store a `List<DomeWindField>` where each DomeWindField holds grid data per layer. Same structure as current profile, just richer fields.
  - **If area time-series does NOT work:** Fetch grid only for the current hour. When forecast slider moves, fetch a new grid for that hour. Cache results per hour to avoid re-fetching.

- [x] Q4: How does `sample()` convert render-space x/z to geographic coordinates?
  - Resolution: The dome center is the user's GPS position (lat/lng from effectivePositionProvider). Render-space x maps to east-west offset: `offsetLng = x * metersPerRenderUnit / (111320 * cos(centerLat * pi / 180))`. Render-space z maps to north-south: `offsetLat = -z * metersPerRenderUnit / 111320` (z negated because dome +z = south, lat + = north). Then `interpolateAtCoord(centerLng + offsetLng, centerLat + offsetLat)`.

- [x] Q5: Should we add procedural turbulence noise as well?
  - Resolution: No, defer to a separate feature. The data-resolution-audit.md recommended it as a visual enhancement, but it is independent of grid fetch. Adding it here would increase scope.

- [x] Q6: What happens when grid fetch fails but point data succeeded?
  - Resolution: Graceful degradation. If grid fetch throws, fall back to point-based data (identical to current behavior). The `DomeWindField` should work with either grid or scalar data transparently.

- [x] Q7: Does `fetchWindGrid` need time-series support for 72 hours?
  - Resolution: Ideally yes, to keep forecast slider working. However, this is the highest-risk item because OGC EDR area + datetime range may not be supported by the APIs. **Recommended approach:** Attempt time-series area query first. If it fails or returns single-timestep data, fall back to fetching grid for current hour only and point data for other hours. This hybrid approach ensures the feature works regardless of API capability.

- [x] Q8: How many API calls does the grid approach require?
  - Resolution:
  - **Best case (area time-series works):** 3 calls total (same as current, just area instead of point)
  - **Worst case (area time-series fails):** 3 area calls for current hour + 3 point-series calls for forecast = 6 calls total
  - **NOT viable:** 3 area calls x 72 hours = 216 calls (too many, would be rate-limited)

## Recommended Approach

### Implementation Strategy

**Hybrid approach with graceful fallback:**

1. **Add 15km and 50km presets** to `DomeInfoBar._sizePresets`

2. **Extend `WindApiClient`** with a `fetchWindGridSeries()` method that attempts area + datetime range. If the API does not support time-series area queries, fall back to single-timestep area query for current hour.

3. **Extend `DomeWindLayer`** to optionally hold a `WindField` grid alongside scalar u/v. The scalar values serve as fallback and as the "center" value for display purposes.

4. **Modify `DomeWindField.sample()`** to use `WindField.interpolateAtCoord()` when grid data is present in the layer. Requires storing center lat/lng and metersPerRenderUnit in the field.

5. **Modify `DomeWindFetcher`** to accept dome radius and switch between point-series and grid-series fetching based on a threshold (15km).

6. **Update `dome_providers.dart`** to pass dome size to the fetcher so it knows whether to fetch grid data.

### Suggested Order of Implementation

1. **DomeInfoBar presets** -- Add 15km/50km buttons (trivial, immediate visual)
2. **WindApiClient.fetchWindGridSeries()** -- Area query with time range support (highest risk item -- test with real API first)
3. **DomeWindLayer grid support** -- Add optional `WindField? grid` field
4. **DomeWindField.sample() spatial interpolation** -- Use grid when available, fall back to scalar
5. **DomeWindFetcher grid-aware fetch** -- Switch logic based on dome size threshold
6. **Provider wiring** -- Pass dome size to fetcher, trigger re-fetch on size change
7. **Tests** -- Grid sample interpolation, fetcher switching, edge cases

### What to Defer (Not MVP Critical)
- Procedural turbulence noise (separate feature, independent of grid data)
- More altitude levels (data-resolution-audit.md confirms current 3 layers are sufficient for dome ceiling at 1800m)
- Grid data for domes outside CONUS (GFS resolution gives poor spatial variation, single-point is fine)
- Time interpolation between forecast hours (current nearest-hour approach is fine)
