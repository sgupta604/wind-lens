## Feature Summary

Enable spatially-varying wind data in the wind dome for large dome sizes (>=15km radius). Currently, all particles at the same altitude receive identical wind vectors regardless of their x/z position. With this feature, particles at different horizontal positions sample a real spatial wind grid, producing visible spatial wind variation across the dome.

### Data Flow: Grid Fetch Path

```
GPS (lat, lng) + domeSize (15000+)
       |
       v
DomeWindFetcher.fetch(lat, lng, radiusMeters: 15000)
       |
       +--> fetchWindGridSeries(lat, lng, radiusKm: 15, pressureLevel: 0,   hours: 72)
       +--> fetchWindGridSeries(lat, lng, radiusKm: 15, pressureLevel: 850, hours: 72)
       +--> fetchWindGridSeries(lat, lng, radiusKm: 15, pressureLevel: 700, hours: 72)
       |
       v  (3 lists of timestamped WindFields)
       |
       +--> assemble into DomeWindProfile
            hourly[0..71]:
              DomeWindField
                layers[0]: DomeWindLayer(alt=10,   u=center.u, v=center.v, grid=WindField)
                layers[1]: DomeWindLayer(alt=1500, u=center.u, v=center.v, grid=WindField)
                layers[2]: DomeWindLayer(alt=3000, u=center.u, v=center.v, grid=WindField)
                centerLat, centerLng, metersPerRenderUnit
```

### Hot-Path: sample() with Grid

```
sample(x=5.2, y=8.0, z=-3.1)
  |
  +-- vertical interpolation: find lo/hi layers, compute frac
  |     lo = layer[1] (1500m), hi = layer[2] (3000m), frac = 0.2
  |
  +-- FOR EACH bounding layer (lo, hi):
  |     if layer.grid != null:
  |       convert (x, z) -> geographic offset from center:
  |         offsetLng = x * metersPerRenderUnit / (111320 * cos(centerLat * pi / 180))
  |         offsetLat = -z * metersPerRenderUnit / 111320
  |       (u, v) = grid.interpolateAtCoord(centerLng + offsetLng, centerLat + offsetLat)
  |     else:
  |       (u, v) = (layer.u, layer.v)
  |
  +-- lerp between lo and hi results using frac
  |
  +-- return WindVector(u, v)

Performance: ~30-40 FLOPs per call (bilinear = 4 mul + 4 add per component,
  coord conversion = 4 mul, vertical lerp = 4 mul + 4 add).
  At 120,000 calls/sec: ~4.8M FLOPs/sec -- negligible on mobile GPU.
```

## Component Specifications

### 1. DomeConstants -- Grid Threshold

Add a single constant:
```dart
/// Dome radius in meters at which grid fetch is used instead of point fetch.
/// Below this, a single point gives sufficient spatial resolution.
/// At 15km radius (30km diameter), HRRR provides ~55-100 grid points.
static const double gridFetchThresholdMeters = 15000.0;
```

### 2. DomeWindLayer -- Optional Grid

Add an optional `WindField? grid` field. When present, `u` and `v` hold the center-point values (for display and fallback). The grid provides spatially-varying data for `sample()`.

```dart
class DomeWindLayer {
  final double altitudeMeters;
  final double u;
  final double v;
  final WindField? grid;  // NEW: spatial grid, null for point-data layers

  const DomeWindLayer({
    required this.altitudeMeters,
    required this.u,
    required this.v,
    this.grid,
  });
}
```

### 3. DomeWindField -- Spatial Interpolation

Add geographic reference fields and rewrite `sample()`:

```dart
class DomeWindField {
  final DateTime validTime;
  final List<DomeWindLayer> layers;
  final double? centerLat;           // NEW
  final double? centerLng;           // NEW
  final double metersPerRenderUnit;  // NEW (default from DomeConstants)
  // ...

  WindVector sample(double x, double y, double z) {
    // ... existing vertical interpolation logic to find lo/hi layers + frac ...

    // NEW: spatial interpolation for each bounding layer
    final loWind = _sampleLayer(layers[lo], x, z);
    final hiWind = _sampleLayer(layers[hi], x, z);

    return WindVector(
      u: loWind.u * (1 - frac) + hiWind.u * frac,
      v: loWind.v * (1 - frac) + hiWind.v * frac,
    );
  }

  /// Samples a single layer at horizontal position (x, z).
  /// If the layer has a grid AND center coordinates are set,
  /// performs bilinear interpolation. Otherwise returns scalar u/v.
  WindVector _sampleLayer(DomeWindLayer layer, double x, double z) {
    final grid = layer.grid;
    if (grid == null || centerLat == null || centerLng == null) {
      return WindVector(u: layer.u, v: layer.v);
    }
    // Convert render-space to geographic offset
    final cosLat = cos(centerLat! * pi / 180);
    final offsetLng = x * metersPerRenderUnit / (111320 * cosLat);
    final offsetLat = -z * metersPerRenderUnit / 111320;
    return grid.interpolateAtCoord(
      centerLng! + offsetLng,
      centerLat! + offsetLat,
    );
  }
}
```

Key design decisions:
- `_sampleLayer` is a private method, not a lambda, to avoid allocation in the hot path.
- `centerLat`/`centerLng` are nullable so existing zero-wind factory and tests still work without passing coordinates.
- `metersPerRenderUnit` defaults to `DomeConstants.metersPerRenderUnit` so existing code does not need to pass it.
- `cos(centerLat)` is computed per sample call (~4ns on ARM). Pre-computing it would save negligible time and complicate the API. If profiling shows otherwise, cache it as a late field.

### 5. WindApiClient -- fetchWindGridSeries()

New method that fetches an area query with a datetime range. Attempts time-series area query first; if the API does not support it (returns error or single-timestep), falls back to single-timestep grid for the current hour.

```dart
/// Fetches a time series of wind grids around a geographic point.
///
/// Returns a list of (DateTime, WindField) for [hours] forecast hours.
/// Tries area+datetime range first. If the API does not support time-series
/// area queries, falls back to a single-timestep area query (current hour only).
///
/// [radiusKm]: Half-width of the bounding box in kilometers.
/// [pressureLevel]: 0 for surface, otherwise hPa.
///
/// Throws if both APIs fail entirely (no data at all).
Future<List<({DateTime time, WindField grid})>> fetchWindGridSeries({
  required double lat,
  required double lng,
  required double radiusKm,
  required int pressureLevel,
  int hours = 72,
})
```

Implementation approach:
1. Build bounding box and WKT POLYGON (reuse `_makeBbox` + `_bboxToPoly`).
2. Attempt Shyft area + datetime range. Parse the time-series response.
3. On Shyft failure, attempt Folkweather area + datetime range.
4. On both time-series failures, fall back to `fetchWindGrid()` for current hour only (single entry).
5. Return list of `({DateTime time, WindField grid})`.

Parsing: Time-series area response likely contains multiple timesteps. For Shyft MultiPointSeries format, the response may have a `t` axis with multiple values and values arrays that are (time * points) in length. For Folkweather, the x/y axes may repeat per timestep.

RISK: If the API format for time-series area queries is substantially different from what we expect, parsing may fail. The fallback to single-timestep grid ensures the feature still works.

### 6. DomeWindFetcher -- Grid-Aware Fetch

Add `radiusMeters` parameter to `fetch()`. When `radiusMeters >= gridFetchThresholdMeters`, switch to grid-based fetching:

```dart
Future<DomeWindProfile> fetch(
  double lat,
  double lng, {
  double radiusMeters = 1000.0,  // NEW: default preserves existing behavior
}) async {
  // Cache key includes radius to separate grid and point caches
  final isGrid = radiusMeters >= DomeConstants.gridFetchThresholdMeters;
  final key = 'dome_${lat.toStringAsFixed(2)}_${lng.toStringAsFixed(2)}_${isGrid ? 'grid' : 'point'}';
  // ... cache check ...

  if (isGrid) {
    return _fetchGrid(lat, lng, radiusMeters);
  } else {
    return _fetchPoint(lat, lng);
  }
}
```

The existing `fetch()` body becomes `_fetchPoint()`. New `_fetchGrid()`:
1. Calls `fetchWindGridSeries()` for 3 pressure levels in parallel.
2. Assembles grid series into `DomeWindField` instances with `grid` on each layer.
3. Falls back to `_fetchPoint()` if grid fetch fails entirely.

### 7. dome_providers.dart -- Pass Dome Size

The `domeWindProfileProvider` needs to watch `domeSizeProvider` and pass it to the fetcher:

```dart
final domeWindProfileProvider =
    FutureProvider<DomeWindProfile?>((ref) async {
  final position = ref.watch(effectivePositionProvider);
  if (position == null) return null;

  final fetcher = ref.watch(domeWindFetcherProvider);
  final domeSize = ref.watch(domeSizeProvider);  // NEW
  return fetcher.fetch(
    position.latitude,
    position.longitude,
    radiusMeters: domeSize,                        // NEW
  );
});
```

This means changing dome size triggers a re-fetch. The cache key in DomeWindFetcher separates grid vs point data, so switching between small and large presets works correctly.

## Implementation Notes

### Design Decisions

1. **Optional grid on DomeWindLayer, not a separate class.** This avoids a parallel class hierarchy. The `grid` field is simply null for point-data layers. `sample()` checks for it and falls back transparently.

2. **centerLat/Lng on DomeWindField, not DomeWindLayer.** All layers in a field share the same geographic center. Putting it on the field avoids redundancy and keeps the layer struct simple.

3. **metersPerRenderUnit on DomeWindField with default.** The dome screen already computes this from `DomeConstants.metersPerRenderUnit`. For grid-aware fields, the fetcher sets it based on the actual dome size. The default preserves backward compatibility.

4. **Cache key includes grid/point distinction.** Prevents stale grid data from being served when the user switches to a smaller dome, and vice versa.

5. **fetchWindGridSeries returns list, not map.** Ordered by time, matching the existing `fetchPointWindSeries` pattern.

6. **cos(centerLat) NOT pre-computed.** At ~4ns per trig call on ARM, 120K calls/sec = ~0.5ms total per second. Pre-computing would add complexity (mutable cached field) for negligible gain. Profile first, optimize later.

### Patterns to Follow

- **Hot-path performance**: No allocations in `sample()`. WindVector is a const-like return. No closures, no lists created.
- **Graceful degradation**: Grid fetch failure -> point data fallback -> zero wind. Never crash.
- **Constructor injection**: WindApiClient mock in tests, same as existing.
- **Static cache**: DomeWindFetcher cache survives provider lifecycle.

### Trade-offs

- **72-hour grid data is large**: 72 hours x 3 levels x ~100 grid points x 16 bytes = ~3.5 MB in memory. Acceptable on modern phones. For 50km domes (~1000 grid points), this grows to ~35 MB. Still acceptable, but we could consider limiting forecast hours for very large domes in a future iteration.
- **API format uncertainty for time-series area queries**: The fallback to single-timestep grid ensures the feature works regardless. Users still get spatial variation for live conditions; forecast hours fall back to point data.

## Non-Goals (Explicitly Deferred)

- **Procedural turbulence noise**: Independent visual enhancement, not part of this feature.
- **Additional altitude levels for dome**: Current 3-layer (surface, 850hPa, 700hPa) mapping is correct for the 1800m dome ceiling.
- **Grid data outside CONUS**: GFS 25km resolution gives 1-4 grid points at 15km radius -- barely worth interpolating. Single-point is fine for non-CONUS users.
- **Time interpolation between forecast hours**: Current nearest-hour approach is standard for weather apps.
- **Large dome rendering optimizations**: LOD, particle density scaling, etc. -- separate feature if needed.
