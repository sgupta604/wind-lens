## Implementation Notes

### Bug 1: keepAlive Annotation

The `@Riverpod(keepAlive: true)` annotation tells the Riverpod code generator to produce a non-auto-dispose provider. This prevents the `SensorNotifiers` (and its `ValueNotifier<double>` objects for heading and pitch) from being disposed during route transitions. The `ref.onDispose` callback in the function body still exists but will only fire when the entire `ProviderScope` is torn down (app exit).

The `lifecycleProvider` (AppLifecycleObserver) independently handles pausing/resuming the `SensorService` when the app backgrounds -- this is unaffected by the keepAlive change.

### Bug 2: ref.read Safety

`ref.read` in `initState` is safe here because:
1. Bug 1 makes `sensorNotifiersProvider` keepAlive -- the `SensorNotifiers` instance is stable for the app's lifetime
2. `SensorNotifiers` is a container for two `ValueNotifier<double>` objects -- its identity never changes
3. Consumers read `.value` directly or use `ValueListenableBuilder`/`super(repaint:)`, not Riverpod rebuilds

### Bug 3: Layer Renumbering

After removing Layer 2 (heading line), the remaining layers shift:
- Layer 3 (altitude rail) -> Layer 2
- Layer 4 (compass bar) -> Layer 3
- Layer 5 (loading indicator) -> Layer 4

The `sensorNotifiers` parameter on `HomeTerrainSection` must remain because `HomeCompassBar` (line 93-94) still uses `widget.sensorNotifiers.heading`.

### Bug 4: Null-Coalescing Assignment

The `??=` pattern for `_camR` is preferred over `late double` because:
- `late` would crash if accessed before first build (unlikely but defensive)
- `??=` only fires once (first build), then preserves user's pinch-zoom adjustments
- Gesture handlers (`_onPointerMove`) can only fire after first build, so `_camR` is guaranteed non-null by then
- The `!` operator is needed when reading `_camR` after the `??=` line, since Dart's flow analysis does not promote nullable fields

## Non-Goals

- NOT converting ARViewScreen's `ref.watch(sensorNotifiersProvider)` to `ref.read` (no reported bug)
- NOT making `gpsPositionProvider` or `rawSensorProvider` keepAlive (they benefit from auto-dispose for subscription cleanup)
- NOT adding new tests (existing coverage is sufficient for these surgical fixes)
- NOT refactoring the provider graph or sensor pipeline
