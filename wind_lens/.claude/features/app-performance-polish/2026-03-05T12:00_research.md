### Startup Provider Chain Analysis

The app startup flow (what fires immediately when HomeScreen builds):

1. `HomeScreen.build()` watches `sensorNotifiersProvider`
2. `sensorNotifiersProvider` watches `rawSensorProvider`
3. `rawSensorProvider` watches `sensorServiceProvider`
4. `sensorServiceProvider` creates `DeviceSensorService()` + `AppLifecycleObserver` -- starts GPS + compass streams immediately
5. `HomeWindRow` watches `sceneStateProvider` + `selectedAltitudeProvider`
6. `sceneStateProvider` watches: `effectivePositionProvider`, `horizonProfileProvider`, `windDataProvider`, `rawSensorProvider`, `selectedAltitudeProvider`
7. `effectivePositionProvider` watches `locationOverrideProvider` + `stablePositionProvider`
8. `stablePositionProvider` watches `gpsPositionProvider`
9. `horizonProfileProvider` watches `effectivePositionProvider` + `horizonProviderServiceProvider` -- fires HeyWhatsThat API call as soon as GPS fix arrives
10. `windDataProvider` watches `effectivePositionProvider` + `selectedAltitudeProvider` + `windDataSourceProvider` -- fires wind API call as soon as GPS fix arrives
11. `HomeTerrainSection` watches `horizonProfileProvider` directly

**Key finding:** GPS, wind API, and terrain API all fire simultaneously the moment a GPS fix arrives. The provider graph has no staging -- `horizonProfileProvider` and `windDataProvider` both watch `effectivePositionProvider` and fire concurrently.

**However:** The UI does appear immediately. `sceneStateProvider` returns `null` while loading, showing "--" placeholders. The terrain section shows procedural fallback while `horizonProfileProvider` is loading. The real issue is likely:
- Sensor service startup (requesting permissions, initializing compass/GPS streams) blocking the main thread
- Multiple HTTP clients initializing simultaneously (WindApiClient, HwtHorizonProvider)
- google_fonts cold-loading adding latency to first text render

1. Be a separate `CustomPaint` layer in the terrain section Stack

## Solutions Needing NEW Research

### A1/A3: Staged Startup Loading

**Current behavior:** All providers fire as soon as their dependencies resolve. GPS, wind, and terrain fetch simultaneously once GPS fix arrives.

**Options for staged loading:**

**Option 1 (Recommended): Deferred provider initialization**
- The current architecture already has natural staging: UI renders immediately with "--" placeholders, terrain shows procedural fallback, particles don't appear until wind data resolves
- The real issue is likely the _perception_ of lag, not actual blocking
- Fix: Add a lightweight loading indicator (shimmer/skeleton) for the wind row while sceneState is null
- Add loading text to terrain section (already exists: "Computing terrain...")

**Option 2: Explicit ordering with Future.delayed**
- Force horizon API to wait until wind API resolves
- Disadvantage: increases total load time, doesn't help perceived performance

**Option 3: Lazy provider initialization**
- Don't watch `horizonProfileProvider` or `windDataProvider` until user interacts
- Disadvantage: data arrives later, confusing UX

**Recommendation:** Option 1 is sufficient. The provider graph already stages naturally. Add visual loading indicators so the app never _feels_ stuck. The main culprits for perceived startup lag are:
1. google_fonts cold-loading (fix: bundle fonts)
2. Sensor permission dialogs (unavoidable)
3. Multiple simultaneous API calls (already handled -- sceneState returns null until all resolve)

### B8: Compass Heading Line

**Implementation approach:**

```dart
class _HeadingLinePainter extends CustomPainter {
  final ValueNotifier<double> headingNotifier;

  _HeadingLinePainter({required this.headingNotifier})
      : super(repaint: headingNotifier);

  @override
  void paint(Canvas canvas, Size size) {
    final heading = headingNotifier.value;
    final x = (heading / 360.0) * size.width;
    final paint = Paint()
      ..color = const Color(0x40FFFFFF)
      ..strokeWidth = 1.0;
    canvas.drawLine(Offset(x, 0), Offset(x, size.height), paint);
  }

  @override
  bool shouldRepaint(_HeadingLinePainter old) => false; // repaint via listenable
}
```

Add as a new layer in `HomeTerrainSection.build()` Stack, between the terrain and altitude rail layers.

**Why this is efficient:**
- `super(repaint: headingNotifier)` means Flutter only repaints THIS painter when heading changes
- Each painter in the Stack has its own `RenderCustomPaint` -- they repaint independently
- No widget rebuild, no Riverpod rebuild, no setState
- The `shouldRepaint` returns `false` because repainting is driven entirely by the listenable
