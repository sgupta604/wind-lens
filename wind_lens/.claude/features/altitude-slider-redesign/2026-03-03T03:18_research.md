## Feature Context

**Goal:** Replace the current 3-discrete-button altitude selector (Surface / MidLevel / JetStream) with a continuous slider having 6 discrete stops at specific pressure levels.

**Target Stops:**

| Stop | Pressure | ~Altitude | Label |
|------|----------|-----------|-------|
| 1 | Surface | 10m | Surface |
| 2 | 850 hPa | 1,500m | 850 hPa |
| 3 | 700 hPa | 3,000m | 700 hPa |
| 4 | 500 hPa | 5,500m | 500 hPa |
| 5 | 300 hPa | 9,000m | 300 hPa |
| 6 | 250 hPa | 10,500m | 250 hPa |

**Depends on:** None (standalone feature)
**Dependency for:** Better multi-level wind visualization

## Design Analysis: Enum Expansion vs Class Replacement

### Option A: Expand the Enum (RECOMMENDED)

Add 3 new values to the existing enum: `level700`, `level500`, `level300`.

```dart
enum AltitudeLevel {
  surface,
  midLevel,     // 850 hPa (rename from "Cloud Level" to "850 hPa"?)
  level700,     // NEW: 700 hPa
  level500,     // NEW: 500 hPa
  level300,     // NEW: 300 hPa
  jetStream,    // 250 hPa (keep existing)
}
```

**Pros:**
- Enum type safety preserved
- Switch expressions still exhaustive (Dart compiler catches missing cases)
- Minimal disruption to existing patterns
- JSON serialization auto-handles new values via `$enumDecode`
- Cache key via `altitude.name` still works

**Cons:**
- 7 switch expressions in `AltitudeLevelProperties` need 3 new cases each (21 new cases)
- Every `switch (altitude)` in prod + test code must add 3 new cases
- Naming: `midLevel` and `jetStream` feel less consistent with `level700` etc.

### Option B: Replace Enum with Sealed Class

```dart
sealed class AltitudeLevel {
  final int pressureHpa;  // 0 for surface, else hPa
  final double metersAGL;
  final String displayName;
  // ...all properties as fields

  static const surface = AltitudeLevel._(0, 10.0, 'Surface', ...);
  static const level850 = AltitudeLevel._(850, 1500.0, '850 hPa', ...);
  // ...
}
```

**Pros:**
- More flexible for future additions
- Properties are fields, not computed switch expressions
- Could support arbitrary pressure levels in the future

**Cons:**
- BREAKS Freezed codegen: `$enumDecode` in `wind_data.g.dart` requires an enum
- BREAKS JSON serialization entirely -- need custom fromJson/toJson
- BREAKS `altitude.name` used in cache keys
- Much larger rewrite scope
- Switch pattern matching changes from exhaustive enum to sealed class patterns

### Option C: Rename All to Pressure-Based Names

```dart
enum AltitudeLevel {
  surface,    // 10m / 0 hPa
  hPa850,     // 1,500m
  hPa700,     // 3,000m
  hPa500,     // 5,500m
  hPa300,     // 9,000m
  hPa250,     // 10,500m
}
```

**Pros:**
- Clean, consistent naming
- Self-documenting pressure level
- Still an enum -- all existing patterns work

**Cons:**
- Renames `midLevel` and `jetStream` -- every reference must update
- Larger diff for cosmetic benefit
- `hPa850` as identifier feels slightly awkward in Dart

### RECOMMENDATION: Option A (Expand Enum)

Keep `surface`, `midLevel`, `jetStream` as they are. Add `level700`, `level500`, `level300`. This is the smallest blast radius while achieving the goal. The existing values' names are already meaningful to the domain and do not need renaming.

Alternative naming for new values: `midUpper` (700), `upperLevel` (500), `subJet` (300) -- but pressure-based names are clearer.

## Property Values for New Altitude Levels

The 3 new stops need interpolated/designed visual properties. Here is a proposal based on existing patterns:

| Level | Pressure | metersAGL | displayName | particleColor | speedMult | parallax | trailScale | streamlinePoints |
|-------|----------|-----------|-------------|--------------|-----------|----------|------------|-----------------|
| surface | 0 | 10 | "Surface" | 0xAAFFFFFF (white) | 1.0 | 1.0 | 1.0 | 12 |
| midLevel | 850 | 1500 | "850 hPa" | 0xAA00DDFF (cyan) | 1.5 | 0.6 | 0.7 | 18 |
| level700 | 700 | 3000 | "700 hPa" | 0xAA00AAFF (blue) | 1.8 | 0.5 | 0.65 | 20 |
| level500 | 500 | 5500 | "500 hPa" | 0xAA8855FF (violet) | 2.2 | 0.4 | 0.6 | 22 |
| level300 | 300 | 9000 | "300 hPa" | 0xAABB33FF (magenta) | 2.7 | 0.35 | 0.55 | 24 |
| jetStream | 250 | 10500 | "250 hPa" | 0xAADD00FF (purple) | 3.0 | 0.3 | 0.5 | 25 |

Notes:
- Colors transition from white -> cyan -> blue -> violet -> magenta -> purple (a continuous spectral gradient)
- Speed multipliers increase roughly linearly from 1.0 to 3.0
- Trail scale and parallax factor decrease linearly
- Streamline trail points increase linearly
- `displayName` for existing `midLevel` changes from "Cloud Level" to "850 hPa" for consistency

## Risk Assessment

### Technical Risks
| Risk | Impact | Likelihood | Mitigation |
|------|--------|------------|------------|
| Shyft API missing 250 hPa | Medium | Low | Already working for jetStream; Folkweather has it as fallback |
| 700 hPa or 500 hPa API errors | Medium | Low | Both Shyft and Folk support these levels; tested in constants |
| Freezed codegen fails after enum change | High | Low | Standard procedure: `dart run build_runner build --delete-conflicting-outputs` |
| Missing switch case causes compile error | Low | High | This is actually a BENEFIT -- compiler catches all missing cases |
| Performance regression from more altitude options | Low | Low | Rendering is identical per-level; only one level active at a time |
| Cache key collision with new altitude names | Low | Very Low | `.name` property is unique per enum value |

### Complexity
- **Level:** Medium
- **Rationale:** The change is conceptually simple (add 3 enum values) but has a large surface area (43 files, 298 references). The altitude slider widget needs a complete redesign. No architectural changes needed -- just extending existing patterns.

## Recommended Approach

### Implementation Strategy

**Expand the enum** (Option A). This is the safest approach with the smallest conceptual change, while the compiler guarantees no missing cases.

### Order of Work

1. **Expand `AltitudeLevel` enum** -- add `level700`, `level500`, `level300` with all 7 properties in the extension. Update `midLevel.displayName` from "Cloud Level" to "850 hPa" and `jetStream.displayName` from "Jet Stream" to "250 hPa".

2. **Run Freezed codegen** -- `dart run build_runner build --delete-conflicting-outputs`. This regenerates `wind_data.freezed.dart`, `wind_data.g.dart`, `scene_state.freezed.dart`, `data_providers.g.dart`.

3. **Fix all switch expressions in production code** -- The Dart compiler will flag every incomplete switch. Fix these in order:
   - `ogc_edr_wind_source.dart` (`_altitudeToPressure`)
   - `altitude_slider.dart` (complete rewrite)
   - `home_altitude_rail.dart` (new tick definitions)
   - `home_wind_row.dart` (`_altitudeValue`)
   - `fake_wind_service.dart` (no change needed -- uses extension property, not switch)

4. **Redesign the altitude slider widget** -- Replace 3-segment layout with 6-stop vertical slider. Keep glassmorphism styling, haptic feedback, and accessibility.

5. **Update all test files** -- Fix test assertions for 6 values, add tests for new values' properties, rewrite slider tests for new UI.

6. **Run full test suite** -- Verify all 798+ tests pass.

### What to Defer (Not Critical for This Change)
- Animating the slider thumb between stops (can be a follow-up polish)
- Changing the home particle painter to visualize all 6 levels simultaneously
- Updating the Wind Dome to fetch all 6 pressure levels (it currently fetches surface/850/700 which is fine)
