## 1. Architecture Overview

This is a rendering fix pass -- NOT an architectural rewrite. All 7 issues live
in the rendering and gesture layer. The data pipeline (DomeWindFetcher,
WindApiClient, providers, DomeWindField.sample(), DomeParticle.tick()) is
untouched.

### What Changes

```
WindDomeScreen (wind_dome_screen.dart)
  |
  +-- Camera sync: theta/phi/camR -> MapController (bearing, zoom, tilt)
  +-- Zoom transition: auto-phi adjustment when camDist crosses thresholds
  +-- Reactive dome size: domeSizeProvider -> domeR/domeH as computed params
  +-- GPS offset fix: raw stablePositionProvider coords for map center
  +-- Multi-touch gesture refinements
  +-- Map tilt: Transform widget wrapping FlutterMap
  |
DomePainter (dome_painter.dart)
  +-- Ground disc: dark filled ellipse drawn BEFORE wireframe
  |
DomeConstants (dome_constants.dart)
  +-- New constants: map zoom, transition thresholds, meters-per-render-unit
```

### Camera Sync Model

```
State: (_theta, _phi, _camR)
         |           |
         v           v
   DomePainter    MapController
   3D scene       bearing + zoom + tilt

theta change -> _mapController.rotate(-theta * 180 / pi)
camR change  -> mapZoom = BASE_MAP_ZOOM - log(camR / BASE_CAM_DIST) / log(2)
phi change   -> _mapTiltAngle = (pi/2 - phi) * 0.6
```

### Zoom Transition Model

```
camR < DOME_THRESHOLD (400):
  Dome prominent, 3D perspective, phi at user-set value

DOME_THRESHOLD < camR < MAP_THRESHOLD (700):
  Transitioning, phi stable

camR > MAP_THRESHOLD (700):
  phi auto-eases toward pi/2 (top-down)
  mapTiltAngle auto-eases toward 0.0
  Map takes over as primary view
```

### Draw Order (DomePainter)

```
1. _drawGroundDisc()     -- dark filled ellipse at y=0
2. _drawFootprint()      -- existing footprint circle at y=0.03
3. _drawWireframe()      -- latitude rings + meridians
4. _drawVerticalAxis()   -- center axis line
5. _drawParticles()      -- wind trail segments
6. _drawUserMarker()     -- center marker + pulsing ring
```

## 4. Detailed Fix Designs

### 4.1 Issue 1 -- Map/Dome Camera Sync

**Problem:** Dome 3D camera (theta, phi, camR) and map camera (bearing, zoom)
are independent. Orbiting the dome leaves the map stationary.

**Fix A -- Bearing Sync:**
After every theta change (single-finger horizontal drag), call:
```dart
_mapController.rotate(-_theta * 180 / pi);
```
The minus sign accounts for map bearing being clockwise-from-north while theta
rotates counter-clockwise in the 3D coordinate system.

**Location:** `_onPointerMove()` single-finger branch (line ~301-305 current).

**Fix B -- Zoom Sync:**
After every camR change (pinch gesture), compute and apply map zoom:
```dart
final mapZoom = DomeConstants.baseMapZoom -
    log(_camR / DomeConstants.baseCamDist) / log(2);
_mapController.move(
  _mapController.camera.center,
  mapZoom.clamp(DomeConstants.minMapZoom, DomeConstants.maxMapZoom),
);
```

**Location:** `_onPointerMove()` two-finger pinch branch (line ~312-321 current).

**Fix C -- Map Tilt:**
Wrap FlutterMap in a Transform widget with perspective:
```dart
Transform(
  alignment: Alignment.center,
  transform: Matrix4.identity()
    ..setEntry(3, 2, 0.001)
    ..rotateX(_mapTiltAngle),
  child: FlutterMap(...),
)
```

New state variable:
```dart
double _mapTiltAngle = 0.0;  // derived from phi
```

Updated every time phi changes:
```dart
_mapTiltAngle = (pi / 2 - _phi) * 0.6;
```

**Location:** `build()` method, wrapping the existing FlutterMap widget.

### 4.2 Issue 2 -- Zoom Transition

**Problem:** No smooth transition between dome-prominent and map-prominent views.

**Fix:** Add `_updateZoomTransition()` called from the tick loop:
```dart
void _updateZoomTransition() {
  if (_camR > DomeConstants.mapThreshold) {
    final t = ((_camR - DomeConstants.mapThreshold) / 300.0).clamp(0.0, 1.0);
    _phi = lerpDouble(_phi, pi / 2.0, t * 0.05)!;
    _mapTiltAngle = lerpDouble(_mapTiltAngle, 0.0, t * 0.05)!;
  }
}
```

Called at the end of `_onTick()`, after particle ticking. This runs every frame
(60 Hz) so the transition is smooth.

**Location:** New private method, called from `_onTick()`.

### 4.3 Issue 3 -- Ground Disc

**Problem:** No dark ground plane under the dome. The dome wireframe floats
over the map without grounding.

**Fix:** New `_drawGroundDisc()` method in DomePainter:
- Project 64 points around the dome footprint at y=0 (ground level)
- Draw filled Path with black 55% opacity
- Draw stroke Path with white 35% opacity, 1.0 strokeWidth
- Called FIRST in paint() before footprint/wireframe

This uses the existing `_project3D()` method -- no new projection math needed.

**Location:** New method in DomePainter, called first in `paint()`.

### 4.4 Issue 4 -- Dome Radius Presets

**Problem:** Tapping 500m/1km/2km updates domeSizeProvider but the dome does
not visually change because DomePainter reads DomeConstants.domeR (a static
const) instead of a reactive parameter.

**Fix:**
1. In WindDomeScreen, compute domeR/domeH from domeSizeProvider:
```dart
final domeSizeMeters = ref.watch(domeSizeProvider);
final domeR = domeSizeMeters / DomeConstants.metersPerRenderUnit;
final domeH = domeR * 0.75;
```

2. Pass computed domeR/domeH to DomePainter (already accepts them as params).

3. When dome size changes, re-initialize particles within the new bounds.
Use `ref.listen(domeSizeProvider, ...)` to detect changes:
```dart
ref.listen(domeSizeProvider, (prev, next) {
  _reinitializeParticles(next);
});
```

The `_reinitializeParticles()` method respawns all particles using the new
domeR/domeH bounds. Also need to update the particle tick call to use the
computed domeR/domeH (not DomeConstants.domeR/domeH).

**Key insight:** The metersPerRenderUnit constant determines visual scale.
At 5.0 m/render-unit: 500m = 100 render units, 1000m = 200, 2000m = 400.
These are large -- the camera distance bounds also need scaling. Instead,
use the existing domeR=18 render units as the "screen target" and let the
conversion happen internally:
```dart
// Keep visual size fixed at DomeConstants.domeR (18 render units)
// The "meters per render unit" changes with dome size
// This way: all zoom/camera/geometry constants stay the same
```

Actually, re-reading the fixes doc more carefully: "DOME_R_RENDER is fixed.
The dome always represents the same physical radius." This means the visual
render radius stays at 18 render units, but the dome REPRESENTS a different
physical area (500m vs 1km vs 2km). The conversion factor changes, not the
render geometry.

So the fix is simpler:
- DomePainter always uses DomeConstants.domeR (18) and DomeConstants.domeH (14)
  for rendering and particle bounds
- domeSizeProvider only affects the velocity scaling and data fetching radius
- The preset buttons update the label in DomeInfoBar (already working via
  domeSizeProvider) and the data fetch radius (future enhancement)

Wait -- the fixes doc says "When dome radius changes, re-initialize particles
to spawn within the new dome bounds" and shows computing DOME_R_RENDER from
domeSizeProvider. Let me re-read...

The fixes doc defines:
```dart
const double METERS_PER_RENDER_UNIT = 5.0;
final DOME_R_RENDER = domeRadiusMeters / METERS_PER_RENDER_UNIT;
final DOME_H_RENDER = DOME_R_RENDER * 0.75;
```

This DOES change the render geometry: 500m/5 = 100, 1000m/5 = 200, 2000m/5 = 400.
But those render units are WAY larger than the current 18-unit dome, which would
break all camera constants.

The correct interpretation: The METERS_PER_RENDER_UNIT needs to be tuned so the
default (1000m) produces the current domeR (18):
```dart
METERS_PER_RENDER_UNIT = 1000.0 / 18.0 = ~55.56
```

Then:
- 500m -> domeR = 500 / 55.56 = 9.0 (smaller dome)
- 1000m -> domeR = 1000 / 55.56 = 18.0 (current)
- 2000m -> domeR = 2000 / 55.56 = 36.0 (larger dome)

Camera constants (camR, camRMin, camRMax) stay fixed, but the dome size changes
relative to the camera. This is correct -- a 2km dome should appear larger than
a 500m dome at the same camera distance.

**Revised fix:**
```dart
static const double metersPerRenderUnit = 1000.0 / domeR;  // ~55.56
```

In WindDomeScreen:
```dart
final domeSizeMeters = ref.watch(domeSizeProvider);
final currentDomeR = domeSizeMeters / DomeConstants.metersPerRenderUnit;
final currentDomeH = currentDomeR * (DomeConstants.domeH / DomeConstants.domeR);
```

Pass `currentDomeR` and `currentDomeH` to DomePainter and particle tick calls.

## 7. Implementation Notes

### 7.1 Key Decisions

1. **Thresholds scaled to camR range:** The fixes doc uses 400/700 thresholds
   but our camR range is 27-90. Thresholds are proportionally placed within
   the actual range. The exact values are tunable on-device.

2. **Ground disc uses existing _project3D:** No new projection code. We reuse
   the same view matrix and focal length already computed for wireframe/particles.

3. **Reactive dome size via ref.watch:** The computed domeR/domeH are local
   variables in the build method, passed to DomePainter. When domeSizeProvider
   changes, build() reruns, DomePainter gets new values, particles are
   respawned. Clean Riverpod reactivity.

4. **Map tilt via Transform widget:** flutter_map does not support native pitch.
   Wrapping in a Flutter Transform with perspective gives a convincing tilt
   effect. The perspective entry (0.001) is standard for 3D-ish transforms.

5. **Forecast slider verified correct:** No code changes needed for Issue 7.
   The ticker reads `ref.read(currentDomeWindFieldProvider)` every frame.

### 7.2 Patterns Followed

- Same Listener-based gesture handling (no pattern change)
- Same ValueListenableBuilder paint trigger (no change)
- Same CustomPainter State Survival Pattern
- DomeConstants as static final/const class (no change)

### 7.3 Trade-offs

- **Map tilt is fake perspective:** Transform widget does not actually tilt the
  map camera. Tiles may look slightly distorted at extreme angles. Acceptable
  for the visual effect.

- **Zoom transition uses linear interpolation per frame:** Not a proper easing
  curve. At 60 FPS with t*0.05, it converges quickly (~20 frames to reach 50%
  of the target). Could add easing later but linear is fine for MVP.

- **Ground disc is 64 segments:** Could use fewer for performance. 64 produces
  a smooth-looking ellipse at all camera angles. At 2 drawPath calls per frame,
  this is negligible compared to 2000 particle segments.

### 7.4 Risk Mitigation

- **MapController.rotate() during ticker:** Calling rotate() 60x/sec during the
  zoom transition could cause flutter_map overhead. Mitigation: only call
  rotate/move when the values actually change (compare to last-sent values).

- **Transform widget on FlutterMap:** Could cause layout issues or touch
  forwarding problems. Mitigation: FlutterMap has interactionOptions set to
  none (no touch), so touch forwarding is not a concern.
