**Problem Statement:**
The current `CompassService` manually reads raw magnetometer and accelerometer data from `sensors_plus` and computes heading with `atan2(event.y, event.x)` plus custom smoothing. Despite two fix attempts (v1 reorder, v2 timer-based rewrite), the compass widget still freezes on real devices. The proposed solution is to replace this manual computation with a native compass package that wraps the OS-level compass API (iOS CLLocationManager.heading, Android rotation vector sensor), which handles sensor fusion, calibration, and smoothing natively.

## Pitch Dependency Analysis

**Critical Finding:** None of the compass packages provide pitch/tilt data. The app uses pitch for:

1. **Sky detection (auto-calibrating):** `_skyDetector.updatePitch(_pitch)` -- used to determine sky fraction based on phone tilt angle. Pitch >= 35 degrees triggers calibration.
2. **Sky detection (pitch-based fallback):** `pitchBasedSkyMask.updatePitch(pitchDegrees)` -- assumes top of screen is sky when phone tilted up.
3. **Debug panel:** Displays current pitch value.

**Conclusion:** `sensors_plus` MUST be retained for accelerometer data to compute pitch. The migration only replaces the magnetometer heading source, not the accelerometer pitch source.

## Open Questions

- [x] Q1: Which package should we use -- flutter_compass or compassx?
  - Resolution: **flutter_compass** is recommended as the primary choice due to 36x more downloads (63k vs 1.75k), wider community validation, and the `headingForCameraMode` field which could be useful for AR. However, it has 43 open issues. If flutter_compass causes build problems or heading issues on device, switch to compassx as fallback.

- [x] Q2: Do we still need sensors_plus after this change?
  - Resolution: **YES.** None of the compass packages provide pitch/tilt data. sensors_plus accelerometer stream is still needed for pitch computation, which is used by sky detection (auto-calibrating and pitch-based) and the debug panel.

- [x] Q3: Should we keep the existing timer-based architecture or simplify?
  - Resolution: **Keep the timer architecture.** It provides consistent 20 Hz emission, decouples sensor rate from UI rate, and all existing tests depend on it. The only change is the heading source (from atan2(mag.y, mag.x) to flutter_compass heading).

- [x] Q4: Should we apply our own smoothing on top of native heading?
  - Resolution: **YES, keep the existing low-pass filter.** Native heading may still have some jitter. The existing _lerpAngle smoothing (factor 0.15 at 20 Hz) provides consistent behavior. If the native heading proves smoother, the smoothing factor can be reduced later.

- [x] Q5: What happens if flutter_compass returns null heading?
  - Resolution: **Fall back to previous value.** Store the last valid heading. If flutter_compass consistently returns null (no sensor available), fall back to the current sensors_plus magnetometer atan2 approach. This requires keeping the magnetometer subscription as a conditional fallback.

- [x] Q6: Will the existing 390 tests still pass?
  - Resolution: **YES.** Tests use `setRawHeading()` and `tick()` test helpers that bypass the actual sensor subscriptions entirely. The heading source (flutter_compass vs magnetometer) is only used in the `start()` method, which tests never call (they use test helpers instead). The test helpers set `_rawHeading` directly, so the computation pipeline (smoothing, emission, lerpAngle) is tested independently of the data source.

- [ ] Q7: Does flutter_compass build correctly with the project's current Gradle/Xcode setup?
  - Recommendation: Must verify during implementation by running `flutter pub get` and attempting a build. If it fails, try compassx instead.
  - Status: NEEDS VERIFICATION DURING IMPLEMENTATION

## Recommended Approach

### Implementation Strategy

**Minimal-change approach:** Replace only the magnetometer heading source in `CompassService.start()`, keeping everything else (timer architecture, smoothing, pitch from accelerometer, test helpers, public API) unchanged.

```dart
// In start(), replace:
_magnetometerSub = magnetometerEventStream().listen((event) {
  _rawHeading = (atan2(event.y, event.x) * 180 / pi + 360) % 360;
}, ...);

// With:
_compassSub = FlutterCompass.events?.listen((event) {
  if (event.heading != null) {
    _rawHeading = event.heading!;
  }
}, ...);
```

**Fallback strategy:** If `FlutterCompass.events` is null (no sensor), fall back to the current magnetometer atan2 approach. This provides backward compatibility for devices where the native compass API is unavailable.
