# Plan: compass-native

## Problem Statement

The current `CompassService` computes heading from raw magnetometer data via `atan2(event.y, event.x)`. Despite two fix attempts (v1 dead zone reorder, v2 timer-based rewrite), the compass still freezes on real devices. The root cause is likely that raw magnetometer data is unreliable without OS-level sensor fusion and calibration. The fix is to replace the heading source with `flutter_compass`, which wraps the native OS compass API (iOS CLLocationManager, Android rotation vector sensor).

## Architecture Overview

```
BEFORE (current):
  sensors_plus magnetometer --> atan2(y,x) --> _rawHeading --> timer(smooth+emit) --> stream
  sensors_plus accelerometer --> atan2(-z,y) --> _rawPitch  --> timer(smooth+emit) --> stream

AFTER (target):
  flutter_compass events --------> heading --> _rawHeading --> timer(smooth+emit) --> stream
  sensors_plus accelerometer --> atan2(-z,y) --> _rawPitch  --> timer(smooth+emit) --> stream
```

The change is surgical: only the heading SOURCE changes. Everything downstream (timer, smoothing, emission, public API, test helpers) stays identical.

```dart
// BEFORE:
_magnetometerSub = magnetometerEventStream().listen(
  (event) {
    _rawHeading = (atan2(event.y, event.x) * 180 / pi + 360) % 360;
  },
  onError: (e) => debugPrint('Magnetometer error: $e'),
);

// AFTER:
_compassSub = FlutterCompass.events?.listen(
  (event) {
    if (event.heading != null) {
      _rawHeading = event.heading!;
    }
    // If heading is null, keep previous _rawHeading value
  },
  onError: (e) => debugPrint('Compass error: $e'),
);
```

### 3. compass_service_test.dart

**Add new test group** after existing groups (around line 740):

```dart
group('Null heading handling (compass-native)', () {
  test('should retain previous heading when native compass returns null', () {
    // Set initial heading, converge, then verify it holds
    compassService.setRawHeading(90.0);
    for (int i = 0; i < 200; i++) {
      compassService.tick();
    }
    expect(compassService.heading, closeTo(90.0, 1.0));
    // _rawHeading stays at 90.0 if flutter_compass sends null
    // (the null guard in start() preserves previous value)
    // Tick again -- heading should still be ~90
    compassService.tick();
    expect(compassService.heading, closeTo(90.0, 1.0));
  });
});
```

**Note:** The null-heading guard is tested indirectly through the existing test helpers. When flutter_compass sends null, `_rawHeading` is not updated, so the smoothing target stays at the previous value. The test above verifies this invariant: if `_rawHeading` is not changed, heading holds steady.

### Test Approach
The existing tests use `setRawHeading()`, `setRawPitch()`, `tick()`, and `simulateMagnetometerEvent()` which bypass the actual sensor subscriptions entirely. Since we are only changing what happens inside `start()` (the real sensor path), and tests never call `start()`, all existing tests will pass unchanged.

The new null-handling tests also use test helpers to verify the invariant that `_rawHeading` retains its value when not explicitly updated.

## Implementation Notes

### Design Decisions

1. **Keep smoothing on top of native heading.** Even though flutter_compass uses OS-level sensor fusion (which includes some smoothing), our existing `_lerpAngle` low-pass filter provides consistent, tunable behavior across devices. Keeping it means the UX is predictable. If native heading proves too smooth (over-damped), the smoothing factor can be increased later.

2. **Keep `simulateMagnetometerEvent` test helper.** Even though the real path no longer uses magnetometer, the test helper is used by 6+ existing BUG-009 regression tests. It computes heading from atan2 and calls tick() -- this is a valid test path regardless of the real sensor source. Renaming it would break tests for no benefit.

3. **No fallback to sensors_plus magnetometer.** The research suggested keeping magnetometer as fallback if `FlutterCompass.events` is null (no sensor). For simplicity, we will handle `FlutterCompass.events` being null by logging a warning and letting `_rawHeading` stay at 0. If this proves insufficient on real devices, a fallback can be added in a follow-up. The null-stream case (`FlutterCompass.events` itself is null) means the device has no compass sensor at all, which is a hardware limitation we cannot work around.

4. **No `dart:math` import removal.** The `dart:math` import is still needed for `atan2`, `pi`, `cos`, `sin` used in `_lerpAngle`, `simulateMagnetometerEvent`, `simulateAccelerometerEvent`, and the accelerometer pitch calculation.

### Patterns

- **Null coalescing for heading:** `if (event.heading != null) _rawHeading = event.heading!;`
- **Null-safe stream subscription:** `FlutterCompass.events?.listen(...)` -- the `?` handles the case where the device has no compass sensor

### Trade-offs

| Decision | Pro | Con |
|----------|-----|-----|
| Keep smoothing filter | Consistent UX, tunable | Possible over-damping if native heading is already smooth |
| No magnetometer fallback | Simpler code, fewer code paths | Devices with broken native compass get no heading |
| Keep simulateMagnetometerEvent | Zero test changes, backward compatible | Name is slightly misleading (no longer matches real path) |

## Non-Goals

- **Not** removing `sensors_plus` dependency (still needed for accelerometer/pitch)
- **Not** using `headingForCameraMode` from flutter_compass (standard `heading` is sufficient)
- **Not** exposing compass accuracy to UI (can add later)
- **Not** switching to `compassx` package (only if flutter_compass has build issues)
- **Not** changing the timer-based architecture or smoothing algorithm
- **Not** modifying any UI components (compass_widget, ar_view_screen, etc.)
- **Not** adding location-based true heading correction

## Risk Mitigation

| Risk | Mitigation |
|------|------------|
| flutter_compass build failure with current Gradle/Xcode | Verify with `flutter pub get` first. If fails, try compassx as alternative. |
| flutter_compass heading always null on some devices | Null guard retains previous value. Worst case: heading stays at 0. |
| flutter_compass event rate is very slow | Timer-based architecture decouples rate. Even 1 Hz native events will work (with smooth interpolation from timer). |
| Existing tests break | Tests use test helpers that bypass start(). Will not break. Verify with `flutter test` before and after. |
