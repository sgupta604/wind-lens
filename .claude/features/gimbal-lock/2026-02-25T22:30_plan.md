## Problem

When the phone is tilted straight up (pitch approaching 90 degrees), the native OS compass heading becomes unreliable due to gimbal lock. The heading can flip ~180 degrees, which reverses wind particle direction and spins the compass widget. The current code passes raw heading through with no pitch-awareness.

## Architecture Overview

### Current Timer Tick (lines 108-117 of compass_service.dart)

```
Timer.periodic(50ms) {
  _smoothedHeading = _lerpAngle(_smoothedHeading, _rawHeading, 0.15)   <-- ALWAYS 0.15
  _smoothedPitch  += (_rawPitch - _smoothedPitch) * 0.15
  emit(CompassData(heading, pitch))
}
```

### Fixed Timer Tick (soft blend)

```
Timer.periodic(50ms) {
  _smoothedPitch  += (_rawPitch - _smoothedPitch) * smoothingFactor    <-- pitch first
  headingAlpha     = _headingAlpha(_smoothedPitch)                     <-- NEW: pitch-aware
  _smoothedHeading = _lerpAngle(_smoothedHeading, _rawHeading, headingAlpha)
  emit(CompassData(heading, pitch))
}
```

### Heading Alpha Computation

```
  pitch (abs)    headingAlpha    behavior
  +-----------+---------------+---------------------+
  | 0 - 65    | 0.15 (full)   | Normal operation    |
  | 65 - 80   | 0.15 -> 0.0   | Gradual freeze      |
  | 80 - 90   | 0.0 (zero)    | Fully locked        |
  +-----------+---------------+---------------------+

  Formula (blend zone):
    headingAlpha = smoothingFactor * (1.0 - (pitchAbs - 65.0) / 15.0)
```

### Data Flow (unchanged)

```

                                     |
                                  (all downstream is unchanged)

        ParticleOverlay                              CompassWidget

```

## Detailed Code Changes

### 1. Add Constants (compass_service.dart, after line 40)

```dart
/// Pitch angle (degrees) below which heading updates normally.
/// Compass is reliable up to roughly 60-65 degrees of tilt.
static const double headingLockStartPitch = 65.0;

/// Pitch angle (degrees) above which heading is fully locked.
/// Above this, compass data is mathematically unreliable (gimbal lock).
static const double headingLockEndPitch = 80.0;
```

### 2. Add Static Helper Method (compass_service.dart, before _lerpAngle)

```dart
/// Computes the effective heading smoothing factor based on pitch.
///
/// At high pitch angles (approaching 90 degrees), compass heading becomes
/// unreliable due to gimbal lock. This method gradually reduces the heading
/// smoothing factor to zero as pitch increases, effectively freezing heading
/// at the last reliable value.
///
/// Returns [smoothingFactor] when |pitch| < [headingLockStartPitch],
/// 0.0 when |pitch| > [headingLockEndPitch], and a linear blend between.
@visibleForTesting
static double headingAlpha(double smoothedPitch) {
  final pitchAbs = smoothedPitch.abs();
  if (pitchAbs < headingLockStartPitch) {
    return smoothingFactor;
  } else if (pitchAbs > headingLockEndPitch) {
    return 0.0;
  } else {
    return smoothingFactor * (1.0 - (pitchAbs - headingLockStartPitch) /
        (headingLockEndPitch - headingLockStartPitch));
  }
}
```

Making this `static` and `@visibleForTesting` allows direct unit testing of the alpha curve without needing a CompassService instance. It uses only static constants so there is zero allocation.

### 3. Modify Timer Callback (compass_service.dart, lines 108-117)

**Before:**
```dart
_emitTimer = Timer.periodic(emitInterval, (_) {
  _smoothedHeading =
      _lerpAngle(_smoothedHeading, _rawHeading, smoothingFactor);
  _smoothedPitch += (_rawPitch - _smoothedPitch) * smoothingFactor;

  _controller.add(CompassData(
    heading: _smoothedHeading,
    pitch: _smoothedPitch,
  ));
});
```

**After:**
```dart
_emitTimer = Timer.periodic(emitInterval, (_) {
  // Smooth pitch first -- pitch itself has no gimbal lock issue
  _smoothedPitch += (_rawPitch - _smoothedPitch) * smoothingFactor;

  // Compute pitch-aware heading alpha (gimbal lock mitigation)
  _smoothedHeading =
      _lerpAngle(_smoothedHeading, _rawHeading, headingAlpha(_smoothedPitch));

  _controller.add(CompassData(
    heading: _smoothedHeading,
    pitch: _smoothedPitch,
  ));
});
```

Key change: pitch is smoothed BEFORE heading, so the alpha computation uses the current tick's pitch, not the previous tick's. This is important because the user could tilt from 0 to 85 degrees in one tick (unlikely but possible with aggressive smoothing lag).

## Implementation Notes

### Why Smooth Pitch Before Heading

The previous code smoothed heading first, then pitch. The new code reverses this order so that `headingAlpha()` uses the current tick's smoothed pitch, not the previous tick's. This ensures the lock engages on the same tick that pitch crosses the threshold.

### Why Static Method

`headingAlpha()` is a pure function of smoothed pitch and static constants. Making it static:
1. Allows direct unit testing without a CompassService instance
2. Makes it clear there is no instance state dependency
3. Zero allocation -- no closure, no object creation

### Performance Cost

Per tick (20Hz = 50 ticks/second):
- 1 `abs()` call on a double (no allocation)
- 1-2 double comparisons
- At most: 1 multiply, 1 subtract, 1 divide (blend zone only)
- Total: ~3-5 nanoseconds additional per tick
- Budget: 50ms per tick; this adds < 0.00001ms

### Why These Thresholds (65/80)

- **65 degrees (start blend):** Compass accuracy degrades around 60-70 degrees. Starting at 65 gives a safety margin before heading noise becomes visible.
- **80 degrees (full lock):** At 80 degrees, the heading data is severely degraded. The 15-degree blend zone (65-80) is wide enough for a smooth perceptual transition.
- These are tunable via static constants if device testing shows different thresholds are needed.

## Non-Goals

- **No CompassData changes.** The `heading` and `pitch` fields remain the same types. No "heading locked" flag for MVP.
- **No debug panel indicator.** The debug panel already shows pitch; users can infer lock state from the pitch value.
- **No haptic feedback.** Could be added later but out of scope for this fix.
- **No user-configurable thresholds.** Static constants are fine; if device testing shows issues, the constants are trivially adjustable.
- **No changes to DeviceSensorService, SensorNotifiers, or any consumer.** The fix propagates automatically through the existing pipeline.
