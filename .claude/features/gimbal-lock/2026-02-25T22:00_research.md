## Where Gimbal Lock Manifests

### The Physics Problem

When a phone is tilted to pitch ~90 degrees (pointing straight up), the device's magnetic field vector is nearly parallel to the gravity vector. The heading computation (which projects the magnetic field onto the horizontal plane) becomes degenerate -- a tiny physical rotation can produce a 180-degree heading jump. This is inherent to the 3D rotation representation and affects ALL compass implementations, including the native OS compass (flutter_compass).

### Where It Shows Up in Code

1. **Layer 1 (CompassService._rawHeading):** `FlutterCompass.events` delivers erratic heading values when pitch is near 90. These get stored in `_rawHeading`.

2. **Layer 2 (Timer tick):** The `_lerpAngle` smoothing chases the erratic `_rawHeading`. With smoothingFactor=0.15, a 180-degree jump gets partially smoothed but still causes visible heading oscillation/reversal over several ticks.

3. **Layer 4-5 (SensorNotifiers -> consumers):** The bad heading propagates all the way to ParticleOverlay and CompassWidget. Particles reverse direction; compass widget spins.

### Why Smoothing Alone Does NOT Fix It

The smoothing factor is 0.15. For a 180-degree heading jump:
- Tick 1: heading moves 27 degrees toward the wrong direction
- Tick 5: heading has moved ~74 degrees
- Tick 10: heading has moved ~126 degrees

At 20Hz this means within 0.5 seconds, the heading has moved over 100 degrees -- clearly visible. Even a lower smoothing factor would only delay the problem, not prevent it.

## Analysis: Where to Inject the Fix

### Option A: CompassService (Layer 2) -- the timer tick

**How:** In the timer callback, check `_smoothedPitch` before updating `_smoothedHeading`. If pitch is above threshold, skip the heading update (keep previous smoothed heading).

**Pros:**
- Earliest possible interception
- All downstream consumers automatically get the locked heading
- Zero allocation (just one comparison and conditional skip)
- The `tick()` test helper works the same way -- testable

**Cons:**
- CompassService is a "dumb" smoother today; adding pitch-awareness is a responsibility change
- But the service already has both heading AND pitch, so the data is present

### Option B: SensorNotifiers provider (Layer 4) -- `sensorNotifiersProvider`

**How:** In the `whenData` callback, check `state.pitch` before writing to `notifiers.heading.value`.

**Pros:**
- Centralized for all ValueNotifier consumers
- Doesn't change CompassService at all

**Cons:**
- The `sensorNotifiersProvider` is Riverpod-generated code; the `whenData` callback is a thin lambda
- Harder to unit test (requires Riverpod test container)
- Still passes the bad heading through CompassService stream to anyone listening to `rawSensorProvider` directly (though currently no one does heading-sensitive work there)

### Option C: DeviceSensorService (Layer 3) -- stream mapping

**How:** In the `_compassSub` listener, check pitch before forwarding heading to `_sensorController`.

**Cons:**
- DeviceSensorService does not currently track pitch independently from heading (they come in the same CompassData event, but pitch is also updated)
- Would need to store "last good heading" state
- More complex, same conceptual location as Option A

### Recommended: Option A -- CompassService timer tick

**Rationale:**
1. **Earliest interception** -- bad heading never leaves the service
2. **All consumers protected** -- stream, getters, ValueNotifiers all get the locked heading
3. **Naturally testable** -- `setRawPitch(85); setRawHeading(newValue); tick(); expect(heading, unchanged)`
4. **Zero allocation** -- one `double` comparison in the hot path
5. **Already has both values** -- `_smoothedPitch` and `_smoothedHeading` are both present in the timer callback
6. **No API change** -- CompassData still has heading and pitch; consumers unaware of the lock

## Recommended Approach: Soft Blend (not hard lock)

### Why Soft Blend Over Hard Lock

A **hard lock** (if pitch > 75: skip heading update entirely) creates a visible discontinuity:
- At 74.9 degrees: heading updates normally
- At 75.1 degrees: heading freezes instantly
- User tilting phone up/down rapidly around the threshold would see heading stutter (update, freeze, update, freeze)

A **soft blend** gradually reduces the heading smoothing factor as pitch increases:

```dart
// In the timer callback, replace the heading update:
final pitchAbs = _smoothedPitch.abs();
final double headingAlpha;
if (pitchAbs < 65.0) {
  headingAlpha = smoothingFactor;  // Normal: 0.15
} else if (pitchAbs > 80.0) {
  headingAlpha = 0.0;  // Fully locked
} else {
  // Linear blend from 0.15 to 0.0 over 65-80 degrees
  headingAlpha = smoothingFactor * (1.0 - (pitchAbs - 65.0) / 15.0);
}
_smoothedHeading = _lerpAngle(_smoothedHeading, _rawHeading, headingAlpha);
```

### Threshold Values

| Pitch Range | Heading Behavior | Rationale |
|-------------|-----------------|-----------|
| 0-65 degrees | Normal (alpha=0.15) | No gimbal lock issues in this range |
| 65-80 degrees | Gradual fade (alpha 0.15 -> 0.0) | Compass increasingly unreliable |
| 80-90 degrees | Fully locked (alpha=0.0) | Heading data is mathematical garbage |

**Why 65/80 and not 70/85:**
- Conservative lower bound (65) -- compass starts losing accuracy around 60-70 degrees; 65 gives a safety margin
- Conservative upper bound (80) -- at 80 degrees the heading noise is already severe; waiting until 85 or 90 would allow visible jitter
- The 15-degree blend zone (65-80) is wide enough for a smooth transition

### Implementation in CompassService

The fix goes in the timer callback (lines 108-117 of `compass_service.dart`):

```dart
_emitTimer = Timer.periodic(emitInterval, (_) {
  // Always smooth pitch (pitch itself doesn't have gimbal lock)
  _smoothedPitch += (_rawPitch - _smoothedPitch) * smoothingFactor;

  // Compute effective heading alpha based on pitch
  // At high pitch, heading from compass is unreliable (gimbal lock)
  // Gradually reduce heading responsiveness to zero
  final pitchAbs = _smoothedPitch.abs();
  final double headingAlpha;
  if (pitchAbs < 65.0) {
    headingAlpha = smoothingFactor;
  } else if (pitchAbs > 80.0) {
    headingAlpha = 0.0;
  } else {
    headingAlpha = smoothingFactor * (1.0 - (pitchAbs - 65.0) / 15.0);
  }

  _smoothedHeading = _lerpAngle(_smoothedHeading, _rawHeading, headingAlpha);

  _controller.add(CompassData(
    heading: _smoothedHeading,
    pitch: _smoothedPitch,
  ));
});
```

**Cost analysis:**
- 1 `abs()` call (no allocation -- returns double)
- 1-2 comparisons
- 1 multiplication + 1 subtraction + 1 division (worst case, in the blend zone)
- Zero object allocation
- Runs at 20Hz, well within the 16ms budget

## Risk Assessment

### Technical Risks

| Risk | Impact | Likelihood | Mitigation |
|------|--------|------------|------------|
| Threshold values wrong (too early/late lock) | Med | Med | User-tunable constants; easy to adjust. Start conservative (65/80) and tighten if needed on device |
| Pitch smoothing lag causes heading lock to activate late | Low | Low | Pitch smoothing uses same 0.15 factor; converges within ~0.5s. For gradual tilt (user tilting phone up), this is fine |

## Open Questions

- [x] Q1: Should the fix be in CompassService or SensorNotifiers?
  - Resolution: CompassService (Layer 2). Earliest interception, all consumers protected, naturally testable.

- [x] Q2: Hard lock or soft blend?
  - Resolution: Soft blend. Smooth transition avoids visual discontinuity at threshold boundary.

- [x] Q3: What pitch thresholds?
  - Resolution: 65 degrees (start blend) to 80 degrees (fully locked). Conservative range that catches gimbal lock before it becomes visually apparent.

- [x] Q4: Should CompassData carry a "heading locked" flag for debug display?
  - Resolution: Not for MVP. The debug panel already shows pitch, and users can infer the lock state from the pitch value. Adding a flag would require changing CompassData, SensorState (Freezed), and SensorNotifiers -- excessive for a debug convenience. Can be added later if needed.

- [x] Q5: What about `_rawPitch` vs `_smoothedPitch` for the threshold check?
  - Resolution: Use `_smoothedPitch`. Raw pitch can be noisy and could cause the lock to flicker on/off rapidly at the boundary. Smoothed pitch provides stable threshold behavior.
