## Architecture Overview

The current wind dome renders a flat 2D scatter of dots because particles live at
real-world lat/lng coordinates and are projected through flutter_map's tile
projection. The fix is a clean two-layer architecture:

```
+--------------------------------------------------------------+
|  Stack (in WindDomeScreen)                                    |
|                                                               |
|  Layer 1: FlutterMap (background)                             |
|    - Dark Carto tiles centered on GPS                         |
|    - InteractiveFlag.none (no map gestures)                   |
|    - ONLY job: show dark map tiles                            |
|                                                               |
|  Layer 2: Positioned.fill + Listener + CustomPaint            |
|    - Self-contained 3D scene in DomePainter                   |
|    - Dome-local coordinates: x,y,z in render units            |
|    - Own camera model: spherical orbit (phi, theta, camR)     |
|    - Own perspective projection: view matrix + proj divide    |
|    - Draws: wireframe, particles, user marker                 |
|    - NO lat/lng, NO flutter_map interaction                   |
|                                                               |
|  Layer 3: DomeInfoBar (top HUD)                               |
|  Layer 4: DomeForecastSlider (bottom HUD)                     |
+--------------------------------------------------------------+
```

### Camera Model (manual perspective projection)

The prototype uses THREE.js `PerspectiveCamera` with `lookAt`. We must port this
to a manual 4x4 matrix pipeline in Dart:

```
World (dome-local x,y,z)
  --> View transform (camera lookAt matrix)
    --> Perspective divide (focal length / z_eye)
      --> Screen coordinates (px)
```

**From prototype (lines 48-59 of wind-dome.jsx):**
```javascript
let phi = Math.PI / 2.8;      // ~64 deg from horizontal, oblique view
let theta = Math.PI / 6;       // initial azimuth ~30 deg
const CAM_R = DOME_R * 2.8;    // camera orbit radius = 50.4

camera.position.set(
  CAM_R * Math.sin(phi) * Math.sin(theta),   // x
  CAM_R * Math.cos(phi),                       // y (up)
  CAM_R * Math.sin(phi) * Math.cos(theta)     // z
);
camera.lookAt(0, DOME_H * 0.2, 0);  // look at y=2.8 (slightly above ground)
```

**Dart implementation:** Build a `lookAt` view matrix from camera position and
target, then project each 3D point to 2D using perspective division:

```dart
// Camera position from spherical coordinates
final cx = camR * sin(phi) * sin(theta);
final cy = camR * cos(phi);
final cz = camR * sin(phi) * cos(theta);

// Build view matrix (right-hand lookAt)
final forward = normalize(target - cameraPos);
final right   = normalize(cross(forward, up));
final camUp   = cross(right, forward);
// view = [ right.x   right.y   right.z   -dot(right,pos) ]
//         [ camUp.x  camUp.y   camUp.z   -dot(camUp,pos) ]
//         [ -fwd.x   -fwd.y    -fwd.z     dot(fwd,pos)   ]
//         [ 0         0         0          1               ]

// Project: screen = focal * (eye.x / eye.z, eye.y / eye.z) + center
```

The `fov` constant from the current code (600.0) is replaced by a proper focal
length derived from the THREE.js camera's 48-degree vertical FOV:
`focal = (canvasHeight / 2) / tan(fov_radians / 2)`

### Dome Geometry (half-ellipsoid)

All geometry is defined in dome-local render units:

```
DOME_R = 18    (radius on ground plane)
DOME_H = 14    (height of half-ellipsoid apex)
```

Ellipsoid equation: `(x^2 + z^2) / R^2 + y^2 / H^2 <= 1.0` with `y >= 0`.

### Draw Order

Matching the prototype's visual layering (back-to-front):
1. Footprint circle on ground plane (y=0.03, opacity 0.5)
2. Dome wireframe: 8 latitude rings + 16 meridian arcs
3. Vertical axis line (y=0.1 to y=DOME_H*0.95, opacity 0.08)
4. Particles (line segments with per-vertex brightness)
5. User position marker (inner dot + pulsing ring + accuracy halo)

- Remove `renderScale` and `speedScale` parameters

  converts m/s to render-units/frame. From prototype line 25: `speed * 0.012`.
  But since `field.sample()` returns u/v in m/s, and we want render-units/frame:
  `x += wind.u * 0.012; z += wind.v * 0.012;` (matches prototype exactly)
- Wait -- the prototype's `sampleWindAtHeight` (line 25) returns
  `vx = cos(dir) * speed * 0.012`. But the Flutter `DomeWindField.sample()` returns
  raw u/v in m/s. So the conversion is: `x += wind.u * VELOCITY_SCALE` where
  VELOCITY_SCALE = 0.012 (render units per m/s per frame). Since we're using dt:
  `x += wind.u * VELOCITY_SCALE * (dt * 60)` to normalize to 60fps baseline.
  Actually simpler: the prototype assumes 60fps with 0.016s per frame. So:
  `x += wind.u * 0.012` per frame. In dt-based: `x += wind.u * 0.72 * dt`
  (because 0.012 * 60 = 0.72 render-units per m/s per second).
- Updraft: `y += 0.002 + (y / domeH) * 0.003` per frame at 60fps.
  In dt-based: `y += (0.12 + (y / domeH) * 0.18) * dt` (multiply by 60)
- Containment: use 1.02 margin factor (prototype line 252: `DOME_R * 1.02`)
- Trail ring buffer: KEEP AS-IS (it already works correctly)
- `respawn()`: KEEP AS-IS (rejection sampling already correct)
- `insideDome()`: KEEP AS-IS (ellipsoid test already correct)

## Implementation Notes

### Key Decisions

1. **lookAt matrix vs. rotation-chain matrix:** The current `_buildCameraMatrix`
   uses a rotation chain (rotateX, rotateY, translate). This doesn't match the
   prototype's camera behavior. We switch to a proper `lookAt` matrix which is
   standard in 3D graphics and directly ports the prototype's camera model.

2. **Focal length from FOV:** The prototype uses `PerspectiveCamera(48, ...)`.
   The focal length for our manual projection is:
   `focal = (canvas.height / 2) / tan(48 * pi / 180 / 2)`
   This gives correct perspective foreshortening that matches the prototype.

3. **dt-based vs. frame-based physics:** The prototype assumes 60fps fixed step.
   We use dt-based physics (multiply constants by 60) for frame-rate independence.
   Constants: `velocityScale = 0.012 * 60 = 0.72`, `updraftBase = 0.002 * 60 = 0.12`.

4. **Wind field sample() altitude conversion:** `DomeWindField.sample()` converts
   render-space y to real-world altitude meters using `maxAltitudeMeters`. The
   formula `altMeters = (y / domeH) * maxAltitudeMeters` stays the same; only
   the constant names change.

5. **No Float64List for trail buffers:** The current `List<double>` ring buffer
   is already zero-allocation (fixed size, pre-allocated). Switching to
   `Float64List` would be a micro-optimization with no measurable benefit since
   Dart's `List<double>` already uses unboxed doubles internally. Keep as-is.

6. **domeSizeProvider interaction:** The user can select dome size (500m, 1km, 2km).
   This changes which altitude range the dome represents, but the RENDER geometry
   stays fixed (domeR=18, domeH=14). The velocity scaling adjusts so particles
   appear to move proportionally faster in a smaller dome.

### Patterns Used

- **CustomPainter State Survival Pattern:** Particle list owned by StatefulWidget,
  passed to painter by reference. Painter never owns mutable state.
- **ValueNotifier repaint trigger:** `_frameCounter` incremented in tick loop,
  `ValueListenableBuilder` triggers repaint without setState.
- **Listener-based multi-touch:** Raw pointer events via `Listener` widget with
  `Map<int, Offset>` for tracking active touches. More reliable than
  `GestureDetector` for simultaneous one-finger and two-finger gestures.

### Trade-offs

- **No depth sorting for particles:** Drawing all particles in array order, not
  sorted by distance from camera. The prototype does the same (THREE.js
  LineSegments with no depth test). At 2000 particles with thin trails, visual
  artifacts from incorrect draw order are negligible.

- **No frustum culling:** All particles are projected even if behind the camera.
  The `_project3D` function returns null for behind-camera points (z_eye <= 0).
  At 2000 particles this is fast enough without spatial culling.

- **No anti-aliasing control:** Flutter Canvas doesn't offer MSAA. The
  `isAntiAlias = true` on Paint handles it adequately for thin line segments.

## Non-Goals

- **Real terrain on ground plane:** The flutter_map background shows map tiles
  but there's no 3D terrain mesh. That's a future feature.
- **Horizontal wind field variation:** `DomeWindField.sample()` ignores x/z
  (uniform wind within dome). Bilinear grid interpolation is future work.
- **Particle color by altitude:** Prototype uses white with brightness only.
  Color-coded altitude particles (like the AR view) are not in scope.
- **Shadow/lighting effects:** No ambient occlusion, no shadow casting. Pure
  wireframe + particle rendering.
- **Compass heading sync:** The prototype doesn't sync dome orientation with
  device compass. Dome orientation is purely user-controlled via drag.
