### Current State Management Pattern

The app uses a **manual StatefulWidget pattern**:

1. `ARViewScreen` (StatefulWidget) creates and owns:
   - `CompassService` instance
   - `FakeWindService` instance
   - `LocationService` instance
   - `AutoCalibratingSkyDetector` instance
   - Stream subscriptions to compass and location
   - All state variables (_heading, _pitch, _skyFraction, _windData, _altitudeLevel, etc.)

2. Data flow: Service -> StreamSubscription -> setState() -> child widgets via constructor params

3. No dependency injection -- services are created directly in `initState()`

4. No shared state -- everything lives in `_ARViewScreenState`

This pattern works but has these problems that SPEC-001 addresses:
- Adding new data sources (HWT, OGC EDR) requires modifying ARViewScreen directly
- No automatic invalidation when upstream data changes
- Compass at 20Hz triggers setState() -> full widget tree rebuild
- No way to swap implementations (mock vs real) without code changes
- No lifecycle management beyond camera (compass/GPS sensors don't pause)

## Gaps Between SPEC-001 and Actual Code

### Gap 1: SkyMask name collision

**SPEC-001 defines two different things named SkyMask:**
1. The existing `SkyMask` abstract interface at `services/sky_detection/sky_mask.dart` (has `skyFraction` and `isPointInSky()`)
2. A new Freezed `SkyMask` data class with `width`, `height`, `pixels: List<bool>`, `method: SkyDetectionMethod`

**Resolution:** The existing `SkyMask` interface should be renamed to `SkyDetector` (which is what SPEC-001 calls the new abstract interface). The new Freezed `SkyMask` is a data class that detectors produce. This is a breaking rename that will touch many files and tests.

### Gap 2: Existing SkyMask interface vs SPEC-001 SkyDetector interface

**Existing SkyMask:**
```dart
abstract class SkyMask {
  double get skyFraction;
  bool isPointInSky(double normalizedX, double normalizedY);
}
```

**SPEC-001 SkyDetector:**
```dart
abstract class SkyDetector {
  Future<SkyMask> detect({
    required CameraFrame frame,
    required SensorState sensors,
    HorizonProfile? horizon,
  });
  String get name;
}
```

These are fundamentally different APIs. The existing one is synchronous and stateful (call `processFrame()` then query `isPointInSky()`). The SPEC-001 one is async and returns a data object. The `AutoCalibratingSkyDetector` does heavy processing in `processFrame()` and caches results -- wrapping it to return a `SkyMask` data class is possible but requires extracting the cached mask into a `SkyMask(width, height, pixels, method)`.

**Resolution:** The wrapper `HsvSkyDetector` will delegate to `AutoCalibratingSkyDetector` internally, call `processFrame()`, extract the cached mask, and return a Freezed `SkyMask`. The existing `isPointInSky()` API in the particle overlay will be migrated to check the `SkyMask.pixels` array directly.

### Gap 3: WindData model redesign

**Existing WindData:**
```dart
class WindData {
  final double uComponent;  // eastward
  final double vComponent;  // northward
  final double altitude;    // meters
  final DateTime timestamp;
  // computed: speed, directionRadians, directionDegrees
}
```

**SPEC-001 WindData:**
```dart
@freezed
class WindData with _$WindData {
  const factory WindData({
    required double speed,        // m/s
    required double direction,    // degrees (meteorological, where wind comes FROM)
    required double gustSpeed,    // m/s
    required AltitudeLevel altitude,
    required DateTime timestamp,
  }) = _WindData;
}
```

Key differences:
- SPEC-001 stores speed+direction instead of u+v components
- SPEC-001 uses `AltitudeLevel` enum instead of raw meters
- SPEC-001 adds `gustSpeed`
- SPEC-001 removes computed getters (speed, direction)

**Resolution:** Need to decide whether to keep u/v components (better for physics/rendering math) or switch to speed/direction (simpler model). The existing particle overlay uses `directionRadians` and `speed` from the WindData -- so the switch is possible. However, the OGC EDR API will return u/v, so keeping both might be useful. Recommendation: Keep u/v internally for computation, but the Freezed model can store both forms. Alternatively, follow SPEC-001 exactly and compute screen angle from speed+direction in the renderer. **Mark as open question for user.**

### Gap 4: CompassData vs SensorState

**Existing CompassData:**
```dart
class CompassData {
  final double heading;
  final double pitch;
}
```

**SPEC-001 SensorState:**
```dart
@freezed
class SensorState with _$SensorState {
  const factory SensorState({
    required double compassHeading,
    required double pitch,
    required DateTime timestamp,
  }) = _SensorState;
}
```

Differences: field name (`heading` -> `compassHeading`), added `timestamp`. This is a minor rename + field addition.

### Gap 5: LocationData vs PositionData

**Existing LocationData:**
```dart
class LocationData {
  final double latitude;
  final double longitude;
  final double accuracy;
  final DateTime timestamp;
}
```

**SPEC-001 PositionData:**
```dart
@freezed
class PositionData with _$PositionData {
  const factory PositionData({
    required double latitude,
    required double longitude,
    required double altitude,  // NEW
    required double accuracy,
    required DateTime timestamp,
  }) = _PositionData;
}
```

Difference: SPEC-001 adds `altitude` field. The existing `LocationService` gets altitude from geolocator's `Position.altitude` but doesn't include it in `LocationData`. This is an easy addition.

### Gap 6: CameraFrame type undefined

SPEC-001's `SkyDetector.detect()` accepts a `CameraFrame` parameter, but this type is never defined in the spec. The existing code uses `CameraImage` from the `camera` package directly.

**Resolution:** Either use `CameraImage` directly (couples interface to camera package) or define a `CameraFrame` wrapper class. Recommendation: Use `CameraImage` in Phase 1 since that is what the existing code uses, then abstract it later if needed. Alternatively, the SkyDetector interface could accept raw byte data (Uint8List) and dimensions instead.

### Gap 7: SensorService combines compass + GPS

SPEC-001 defines `SensorService` with both `sensorStream` (compass/pitch) and `positionStream` (GPS). Currently these are two separate services (`CompassService` and `LocationService`) with different start patterns:
- `CompassService.start()` is synchronous (void)
- `LocationService.start()` is asynchronous (Future<void>) because it needs to request permissions

**Resolution:** The `DeviceSensorService` implementation can own both internally but expose them as separate streams on the interface. The async nature of GPS permission needs to be handled at the implementation level, not the interface level.

### Gap 8: Existing tests reference current class names

405 tests reference `CompassData`, `LocationData`, `WindData`, `SkyMask`, `FakeWindService`, `CompassService`, `LocationService` by name. All of these will need updates when classes are renamed/moved. This is a significant risk for test breakage.

**Resolution:** Phased approach -- when converting a model, update its tests in the same step. When wrapping a service, the wrapper uses the existing class internally, so tests of the underlying class can remain. When renaming (SkyMask -> SkyDetector), update all import paths and references at once.

## Open Questions

- [x] Q1: Should the 3-phase split be used as described by the user?
  - Resolution: YES. The user explicitly designed this split to manage agent context window. Phase 1 establishes foundations, Phase 2 wires them up, Phase 3 adds polish. DECISIONS.md is the handoff mechanism.

- [x] Q2: Should WindData keep u/v components or switch to speed/direction as SPEC-001 specifies?
  - Resolution: **Keep u/v as primary fields**, speed/direction as computed getters. Reasons: (a) OGC EDR API returns u/v natively — storing speed/direction means wasteful round-trip conversion, (b) particle physics uses u/v directly (`particle.x += u * dt`) — storing speed/direction means trig per particle per frame (2000 particles * 50fps = unnecessary work), (c) speed/direction are only needed for UI display/debug. Add `gustSpeed` and `AltitudeLevel altitude` from SPEC-001. Add `factory WindData.fromSpeedDirection()` for mock data convenience.

- [x] Q3: What to do about the SkyMask name collision (interface vs data class)?
  - Resolution: Rename existing `SkyMask` interface to `SkyDetector`. Create new Freezed `SkyMask` data class. This matches SPEC-001's naming. The rename touches ~10 files but is mechanical.

- [x] Q4: Should HSV be converted to Freezed?
  - Resolution: NO. HSV is used in pixel processing hot paths (potentially thousands per frame). Freezed overhead (immutable copies) would hurt performance. It already has manual == and hashCode. Leave it alone.

- [x] Q5: Should Particle be converted to Freezed?
  - Resolution: NO. Particle is intentionally mutable with pre-allocated Float32Lists. It is mutated 2000 times per frame in the render loop. Freezed immutability would be catastrophic for performance.

- [x] Q6: What about `CameraFrame` type in SkyDetector interface?
  - Resolution: Use `CameraImage` from the camera package directly for now. The interface lives in `lib/core/services/` which should be pure Dart, but CameraImage is a data class, not a Flutter widget. If this causes issues, create a thin `CameraFrame` wrapper. Alternatively, pass raw bytes + dimensions instead of CameraImage. **Recommend: pass CameraImage for pragmatism in Phase 1, refine later if needed.**

- [x] Q7: Should we use Hive/Isar for horizon caching or simpler approach?
  - Resolution: For Phase 3, use simple JSON file persistence (path_provider + dart:io). Horizon profiles are small (~360 doubles + metadata). No need for a database dependency. Can upgrade to Hive/Isar later if storage needs grow.

- [ ] Q8: Should PerformanceManager be wrapped in an interface or remain as-is?
  - Recommendation: Keep as-is. It's a pure logic class with no external dependencies. No need to swap implementations. It can be provided via a simple Riverpod provider for testability.
  - Status: RESOLVED (keep as-is, low priority to change)

## Implementation Process Rules (SPEC-001 specific)

This refactor touches every file in the project. It is too large for a single `/implement` run due to agent context limits. These rules apply ONLY to SPEC-001 — after this refactor, features will be modular and fit in normal single-phase pipeline runs.

### 3-Phase Implementation

Each phase gets its own `/implement` call with a fresh agent context:

| Phase | Scope | Checkpoint |
|-------|-------|-----------|
| Phase 1 | Freezed deps + models (one at a time, PositionData first) + service interfaces + wrap existing code | Tests green, commit to branch |
| Phase 2 | Riverpod provider graph + directory restructure + wire AR view to SceneState | Tests green, commit to branch |
| Phase 3 | Lifecycle management + caching layers + integration tests | Tests green, commit to branch |

### DECISIONS.md Handoff

Each `/implement` phase MUST append to `.claude/features/architectural-foundation/DECISIONS.md` at the end of its run. Record:
- What was built and why
- Any deviations from the plan or SPEC-001
- Patterns established (naming conventions, file organization, test approach)
- Known issues or things deferred to next phase

Each subsequent phase MUST read DECISIONS.md before starting work.

### Read Before Write Rule

Each `/implement` phase MUST read the actual current source files before making changes. Do not assume anything about file contents from the plan or spec — read the code as it exists. An agent that reads before writing will self-correct. An agent that assumes and writes blind is where things go wrong.

### Why Sequential, Not Parallel

The 10 tasks have tight sequential dependencies (models → interfaces → wrappers → providers → directory restructure). Two agents editing the same files would cause merge conflicts. Parallel agents make sense AFTER this refactor when features are modular and independent.

### Service Interfaces Before Directory Restructure

Do tasks 2-3 (interfaces + wrap existing code) BEFORE task 4 (directory restructure). That way if the restructure breaks imports, the logic layer is already clean and testable.

### WindData Decision

Store u/v as primary fields. Speed/direction as computed getters. Reasons:
- OGC EDR API returns u/v natively — no wasteful round-trip conversion
- Particle physics uses u/v directly (`particle.x += u * dt`) — no trig per particle per frame
- Add `factory WindData.fromSpeedDirection()` for mock data convenience
