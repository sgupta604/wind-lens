# Research: wind-dome-fixes

## Summary

On-device testing of the wind-dome feature (implemented 2026-02-27) revealed 5 discrete rendering/gesture issues. The data pipeline is confirmed working — real wind data displays correctly (5.9 m/s), the forecast slider is functional, and the Live badge renders. All issues are confined to the rendering and interaction layer.

## Evidence

### Screenshots
- **Current (broken):** `.claude/features/wind-dome/wind_dome_current.PNG`, `wind_dome_current2.PNG`
  - Tiny white blob of particles clustered in center of map
  - No wireframe dome visible at all
  - No 3D perspective — looks completely flat/top-down

  - No multi-touch gesture support
- **Prototype (goal):** `.claude/features/wind-dome/prototype.png`

  - Particles spread across full dome volume at multiple altitudes
  - Clear spatial depth with particles at different heights
  - User marker at dome center

## Issue 1: Projection Bug (Critical)

**Symptom:** Dome renders as flat top-down orthographic blob with no 3D perspective.

**Root cause:** The default `phi` angle in the camera matrix is likely set near `pi/2` (90° from zenith = straight down), producing a top-down view. The prototype uses `phi = pi/2.8` (~64° from zenith, or ~26° above horizontal), giving the characteristic oblique perspective.

**What to verify:**
- Check `_buildCameraMatrix()` in `dome_painter.dart` — is it actually being applied to ALL drawn geometry (particles AND wireframe rings)?
- Check the default phi value — if it's `pi/2` or close, that explains the flat appearance
- Check if wireframe ring coordinates collapse to near-identical screen positions under the current projection

**Fix:** Set default phi to `pi/2.8`. Verify camera matrix transforms all geometry consistently.

## Issue 2: Scale / DOME_R_RENDER (Critical)

**Symptom:** Dome is tiny on screen — appears as a small cluster rather than filling a significant portion of the display.

**Root cause:** `DOME_R_RENDER` is almost certainly set to a raw meter value (e.g., 800) without conversion to render units. 800 meters means nothing to the CustomPainter — it needs logical pixel-scale values (approximately 150-200 logical pixels of radius to look right on screen).

**Fix:** Define a `RENDER_SCALE` constant that converts meters to render units. Apply it consistently everywhere in `DomePainter`. The dome radius in render space should be approximately `min(size.width, size.height) * 0.35` or similar screen-relative sizing.

## Issue 3: GPS Offset

**Symptom:** Dome center is visibly offset from actual GPS position on the map.

**Root cause:** The `stablePositionProvider` rounds GPS coordinates to 2 decimal places for cache keying (`lat.toStringAsFixed(2)`). This introduces ~1.1km of quantization error. If the dome center is anchored to the rounded cache-key coordinates rather than the raw GPS fix, it will land noticeably off from the actual position.

**Fix:** Both map center and dome center must use raw `stablePositionProvider` coordinates (the actual lat/lng values), not the rounded cache key. The cache key rounding is only for the `DomeWindFetcher` HTTP request deduplication — it should never affect rendering positions.

## Issue 4: Gesture System

**Symptom:** Only single-finger drag for orbit. No multi-touch support for zoom, tilt, or rotation.

**Required gesture set:**
| Gesture | Action |
|---------|--------|
| 1-finger drag horizontal | Orbit azimuth (theta) |
| 1-finger drag vertical | Nothing (or subtle tilt) |
| 2-finger pinch | Zoom (adjust camDist) |
| 2-finger vertical drag | Perspective tilt (phi between pi/2 and pi/2.8) |
| 2-finger rotate | Sync map bearing (theta) |

**Root cause:** Flutter's `GestureDetector` can't handle multi-touch natively.

**Fix:** Replace `GestureDetector` with `Listener` widget using `onPointerDown`/`onPointerMove`/`onPointerUp` events. Track pointer IDs manually with `Map<int, Offset> _activePointers`. Detect gesture type based on pointer count:
- 1 pointer: orbit
- 2 pointers: compute pinch distance delta (zoom), vertical centroid delta (tilt), angle delta (rotation)

## Issue 5: Dome Size Control

**Symptom:** No UI control for dome radius. With the current rendering being broken, the feature is non-demonstrable without being able to adjust size.

**Fix:** Add 3-preset size buttons (500m / 1km / 2km) to the UI. Create a `domeSizeProvider` (`StateProvider<double>`) that feeds `DOME_R_METERS` into both the fetcher (for API query radius) and the painter (for render calculations).

**Location:** Either in `DomeInfoBar` or as floating buttons on the dome screen.

## Architecture Assessment

**What works (do NOT change):**
- Data pipeline: `WindApiClient.fetchPointWindSeries()` → `DomeWindFetcher` → `DomeWindProfile` → `DomeWindField`
- Models: `DomeWindLayer`, `DomeWindField.sample()` vertical interpolation, `DomeParticle` with ring buffer trails
- Providers: `domeWindProfileProvider`, `currentDomeWindFieldProvider`, `hoursAheadProvider`
- UI: Info bar, forecast slider, Live/Fcst badge, back button navigation
- Test suite: 697 tests passing (628 existing + 69 new dome tests)

**What needs fixing (rendering + gesture layer only):**
- `dome_painter.dart` — projection matrix, scale conversion, wireframe rendering, particle spread
- `dome_constants.dart` — add RENDER_SCALE, fix default phi
- `wind_dome_screen.dart` — gesture handling, GPS centering
- `dome_providers.dart` — add domeSizeProvider
- `dome_info_bar.dart` or new widget — size preset buttons

## Priority Order

1. Projection fix (phi + camera matrix) — highest impact, makes everything else visible
2. Scale fix (RENDER_SCALE) — dome fills screen properly
3. GPS center fix — dome aligns with actual position
4. Gesture system — proper multi-touch interaction
5. Dome size control — user can adjust radius

## Scope

These are focused fixes — estimated 20-30 modified lines per fix. No architectural changes. No new service files. No model changes. Purely rendering and interaction layer adjustments to existing files.

## Open Questions

None — diagnosis is complete and all fixes are well-defined.
