## 1. Overview

The Wind Dome data pipeline is confirmed working -- real wind data at 5.9 m/s, forecast slider
functional, Live badge rendering. Five discrete rendering and gesture bugs prevent the dome from
looking like the prototype (oblique 3D perspective with visible wireframe rings and spread particles).
These are focused fixes in the rendering and interaction layer only; no architecture changes needed.

### Current vs Target

**Current (screenshots):** Tiny white blob of particles clustered at center. No visible wireframe
rings. No 3D perspective -- looks flat/top-down. Dome occupies maybe 30x30 pixels on screen.

**Target (prototype):** Wide oblique-angle dome filling most of the screen width. Clear latitude
rings visible with perspective foreshortening. Particles spread across the dome volume at
multiple altitudes. User marker visible at center. Map visible underneath.

## 3. Fix Details

### Fix 1: Projection (phi + camera matrix)

**Problem:** The camera matrix builds rotation then translation, but the default phi
(pi/2.8 ~ 1.12 radians) combined with the translate pushes the camera to a near-top-down
view. The `v.z.abs()` in the perspective division also flattens depth.

**Root cause analysis:** Looking at `_buildCameraMatrix`:
```dart
m.rotateY(theta);
m.rotateX(phi);
m.translate(Vector3(0, -domeH * 0.25, -camDist));
```
The Matrix4 operations compose right-to-left. The translate happens in the rotated frame.
With phi ~ 1.12 rad (64 degrees from horizontal), the -camDist translation pushes the
camera mostly downward rather than backward, creating a near-top-down view.

**Fix:** Restructure the camera to orbit-camera pattern:
1. Translate camera back by camDist along -Z (in world space)
2. Rotate around X by phi (tilt down)
3. Rotate around Y by theta (orbit)
4. Apply a small upward shift so dome base is visible

```dart
vm.Matrix4 _buildCameraMatrix(double theta, double phi, double camDist) {
  final m = vm.Matrix4.identity();
  // Orbit camera: rotate scene, then push away
  m.translate(vm.Vector3(0, 0, -camDist));
  m.rotateX(phi);
  m.rotateY(theta);
  m.translate(vm.Vector3(0, -domeH * 0.3, 0));
  return m;
}
```

Also change `_project` to use signed z (not abs) for proper perspective:
```dart
final scale = fov / (fov + v.z);  // v.z is positive (in front of camera)
```

The `v.z.abs()` was preventing proper depth-based foreshortening for objects at
different distances from the camera.

**Files:** `dome_painter.dart` (lines 76-95)

### Fix 2: Scale

**Problem:** `domeRRender = 18.0` render units. With `fov = 600`, the projected dome
radius is approximately `18 * 600 / (600 + 45) ~ 16.7 pixels`. This makes the dome a
tiny blob on screen.

**Fix:** Scale the dome to fill a meaningful portion of the screen. Two approaches:

Option A (simpler): Increase `domeRRender` to ~150 and adjust `domeHRender` and `camDist`
proportionally. This keeps fov=600 but makes the render-space dome large enough to project
to ~200px radius.

Option B: Keep domeRRender small but decrease fov (move camera closer). Risk: extreme
perspective distortion at low fov.

**Chosen: Option A.** Set `domeRRender = 150.0`, recalculate `domeHRender` from aspect
ratio, and set `camDist = domeRRender * 2.5 = 375`. The `renderScale` factor for
particle velocity (domeRRender / domeRMeters) updates automatically since it is already
computed from domeRRender.

**Files:** `dome_constants.dart` (lines 19-26, 44-51)

### Fix 3: GPS Offset

**Problem:** `DomeWindFetcher.fetch()` builds cache key as:
```dart
final key = 'dome_${lat.toStringAsFixed(2)}_${lng.toStringAsFixed(2)}';
```
This quantizes to ~1.1km grid. The map centers on raw `stablePositionProvider` coordinates,
but the cached wind data is for a different (rounded) point. This is fine for wind data
accuracy (wind does not vary within 1km), but creates a visual offset if the map center
and dome center diverge.

**Fix:** The cache key rounding is intentional and correct for cache deduplication. The
actual issue is that `DomeWindProfile.lat/lng` stores the raw fetch coordinates, which is
correct. The map center and dome center both use `stablePositionProvider` directly.

After re-reading the code: the map re-centers on `stablePositionProvider` via `ref.listen`,
and the dome is always drawn at screen center (0,0 in dome-local coordinates). The visual
offset seen is actually caused by Fix #1 (bad projection) and Fix #2 (tiny scale), not by
GPS rounding. The cache key rounding only affects which cached data is returned, not where
the dome is drawn.

**Revised assessment:** This is a non-issue once Fix #1 and #2 are applied. The dome is
always drawn at the center of the CustomPaint canvas, which is Positioned.fill over the
map, which is centered on GPS. Keep the cache key as-is (it is the correct pattern per
CachedWindDataSource). Mark this as "verify after Fix 1+2" rather than a code change.

**Files:** None (verify only)

### Fix 4: Gesture System

**Problem:** `GestureDetector` with `onPanUpdate` only handles single-finger drag for
orbit (theta). No pinch-to-zoom (camDist) or 2-finger vertical drag (phi tilt).

**Fix:** Replace `GestureDetector` with `Listener` widget and track active pointers manually
using a `Map<int, Offset> _activePointers` on the State.

Gesture mapping:
- **1 finger drag:** Orbit azimuth (theta += dx * sensitivity)
- **2 finger pinch:** Zoom (camDist changes proportional to pinch delta)
- **2 finger vertical drag:** Perspective tilt (phi changes)

```dart
Map<int, Offset> _activePointers = {};
double _camDist = DomeConstants.camDist;

void _onPointerDown(PointerDownEvent e) {
  _activePointers[e.pointer] = e.localPosition;
}

void _onPointerMove(PointerMoveEvent e) {
  final prev = _activePointers[e.pointer];
  _activePointers[e.pointer] = e.localPosition;
  if (prev == null) return;

  if (_activePointers.length == 1) {
    // Single finger: orbit
    final dx = e.localPosition.dx - prev.dx;
    _theta -= dx * 0.007;
    _mapController.rotate(-_theta * 180 / pi);
  } else if (_activePointers.length == 2) {
    // Two fingers: pinch + tilt
    final pointers = _activePointers.values.toList();
    // ... calculate pinch distance delta for zoom
    // ... calculate vertical center delta for phi tilt
  }
  setState(() {});
}

void _onPointerUp(PointerUpEvent e) {
  _activePointers.remove(e.pointer);
}
void _onPointerCancel(PointerCancelEvent e) {
  _activePointers.remove(e.pointer);
}
```

### Fix 5: Dome Size Control

**Problem:** Dome radius is hardcoded at 800m in `DomeConstants.domeRMeters`. No user
control for dome coverage area.

**Fix:** Add 3 presets (500m / 1km / 2km) as a `StateProvider<double>` and render preset
buttons in `DomeInfoBar`.

New provider:
```dart
// dome_providers.dart
final domeSizeProvider = StateProvider<double>((ref) => 800.0);
```

UI in DomeInfoBar: Three small pill buttons below the wind speed, showing "500m", "1km", "2km".
Active preset is white, others are dim.

DomePainter and particle tick loop read the provider to compute render-space dome dimensions:
```dart
final domeRMeters = ref.watch(domeSizeProvider);
final domeRRender = domeRMeters * DomeConstants.renderScale;
final domeHRender = DomeConstants.domeHMeters / DomeConstants.domeRMeters * domeRRender;
// Wait -- renderScale is derived from domeRMeters which is now variable.
```

**Revised approach:** Since `renderScale` is defined as `domeRRender / domeRMeters`, and we
want the on-screen dome size to stay the same regardless of real-world radius (the dome
always fills the same screen area, but covers more geographic area), we should keep
`domeRRender` constant at 150 (the new scaled value from Fix #2). Only `domeRMeters` changes,
which means `renderScale` changes, which means particles move at different pixel-rates
(slower for larger dome, faster for smaller dome -- physically correct).

The dome size provider drives:
1. `DomeConstants.domeRMeters` equivalent (passed through to particle tick as meters-per-render-unit)
2. Future: DomeWindFetcher grid fetch radius
3. UI display in DomeInfoBar

**Files:**
- `dome_providers.dart` -- add `domeSizeProvider`
- `dome_info_bar.dart` -- add size preset buttons
- `wind_dome_screen.dart` -- read domeSizeProvider, pass to particle tick and painter
- `dome_constants.dart` -- add helper method or make domeRMeters instance-configurable

## 6. Implementation Notes

### 6.1 Key Decisions

1. **Scale via larger domeRRender (not smaller fov):** Increasing domeRRender to 150 gives
   a predictable dome screen size. Decreasing fov would cause extreme perspective distortion.
   The renderScale factor (domeRRender/domeRMeters) automatically adjusts particle velocities.

2. **Camera as orbit-camera pattern:** Standard 3D orbit camera: translate(-camDist on Z),
   rotateX(phi), rotateY(theta). This is the conventional order for an orbiting camera
   and gives correct perspective at all angles.

3. **Listener over GestureDetector:** Flutter's GestureDetector uses gesture arenas that
   delay recognition and cannot track individual pointer IDs. Listener gives raw pointer
   events with pointer IDs, enabling clean multi-touch tracking with zero delay.

4. **GPS fix is a non-issue:** The dome is always drawn at canvas center, which overlays
   the map center, which tracks raw GPS. The cache key rounding only affects data staleness,
   not dome position.

5. **Dome size presets on-screen size is constant:** All three dome size presets render
   the dome at the same pixel size. What changes is the real-world coverage (500m vs 2km)
   and the particle velocity scale (particles in a 2km dome move slower in pixels because
   the same screen distance represents more meters).

### 6.2 Patterns Followed

- StateProvider for simple user preferences (same as hoursAheadProvider, selectedAltitudeProvider)
- Listener for raw pointer events (standard Flutter pattern for multi-touch)
- Constants centralized in DomeConstants (existing pattern)
- CustomPainter receives all rendering parameters as constructor args (existing pattern)

### 6.3 Risk Mitigation

- **Projection math wrong:** Test on device after each sub-fix. The orbit camera pattern is
  well-documented and the default phi/theta/camDist values give a known-good view.
- **Performance regression from larger dome:** domeRRender=150 means larger coordinate
  ranges but the same number of particles (2000) and same number of draw calls. No
  performance impact expected. PerformanceManager is still active as safety net.
