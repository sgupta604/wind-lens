## Why v1 Failed

The v1 fix reordered dead zone after smoothing but kept both inside the sensor callback. This did NOT work on device. The dead zone still permanently suppresses stream emission once the smoothed value converges close to the raw value (delta < 1.0 degree). The fundamental problem is architectural: smoothing, dead zone gating, and emission are all coupled inside the sensor callback, creating an inherent convergence trap on the emission path.

See `diagnosis_v2.md` for the full mathematical proof and failure analysis.

## Architecture: Timer-Based Decoupled Design

### Current Architecture (Broken)

```
Sensor Event (50-100 Hz)
    |
    v
[Compute raw heading]
    |
    v
[Compute delta = raw - smoothed]
    |
    v
[Apply smoothing: smoothed += delta * 0.1]
    |
    v
[Dead zone gate: delta < 1.0?] --YES--> return (BLOCKS emission)
    |
    NO
    v
[_emitUpdate() to stream]
```

Problem: After ~35 events, smoothed converges to within 1.0 degree of raw. Delta stays below dead zone. Stream goes permanently silent.

### New Architecture (Timer-Based)

```
Sensor Callbacks (50-100 Hz)       Timer (20 Hz / 50ms)
    |                                  |
    v                                  v
[Store _rawHeading]              [_lerpAngle: smoothed -> raw]
[Store _rawPitch]                [Linear lerp: pitch -> raw]
[No processing]                      |
[No emission]                        v
                                [Always emit to stream]
                                [No dead zone gate]
```

The three concerns are fully decoupled:

| Concern | Where | Rate | Responsibility |
|---------|-------|------|----------------|
| Raw sensor capture | Sensor callbacks | Hardware rate (50-100 Hz) | Store latest raw value only |
| Smoothing | Timer callback | Fixed 20 Hz | Circular lerp heading, linear lerp pitch |
| Emission to UI | Timer callback | Fixed 20 Hz | Always emit (no dead zone) |

### Why No Dead Zone Is Needed

The low-pass smoothing filter IS the jitter suppression. When stationary:
- Raw sensor noise oscillates around the true heading
- The smoothing filter absorbs oscillations
- Smoothed output changes by fractions of a degree per tick
- Flutter's rendering pipeline skips repaints when values have not changed meaningfully
- `CompassWidget.shouldRepaint` uses equality check, preventing unnecessary paints

### Key Algorithm: `_lerpAngle`

Handles 0/360 wraparound correctly using shortest-path angular interpolation:

```dart
double _lerpAngle(double from, double to, double t) {
  double diff = (to - from + 540) % 360 - 180;  // shortest angular distance
  return (from + diff * t) % 360;                 // interpolate along short path
}
```

Examples:
- from=350, to=10: diff = (10-350+540)%360-180 = 200%360-180 = 20. Result: 350 + 20*t (goes clockwise through 360/0)
- from=10, to=350: diff = (350-10+540)%360-180 = 880%360-180 = 160-180 = -20. Result: 10 - 20*t (goes counterclockwise)

## Implementation Notes

### Why smoothingFactor increases from 0.1 to 0.15

At the old hardware rate (50-100 Hz) with factor 0.1, the effective time constant was ~10 ticks = 100-200ms. At the new timer rate (20 Hz) with factor 0.15, the time constant is ~6.7 ticks = 335ms. This is slightly more smoothed but provides a good balance between responsiveness and jitter suppression for a compass display. The diagnosis recommends 0.15.

### Why removing dead zones is safe

Dead zones were added to prevent jitter, but the smoothing filter itself suppresses jitter. With timer-based emission at 20 Hz:
- Stationary: smoothed heading changes by < 0.01 degree per tick (sensor noise absorbed by low-pass filter)
- `CompassWidget.shouldRepaint` returns false when heading has not changed (equality check)
- Flutter does not repaint widgets whose `shouldRepaint` returns false
- 20 Hz emission is well within Flutter's 60 FPS rendering budget

### Risk Assessment

- **Risk:** Medium (full service rewrite vs. targeted fix)
- **Mitigating factors:**
  - Same public API -- no downstream changes needed
  - Simpler code (100 lines vs. 203 lines)
  - Well-understood timer pattern (standard in production Flutter compass apps)
  - Comprehensive regression tests validate behavior
  - Backward-compatible test helpers ensure existing test patterns work
- **Regression risk:** Low. All existing consumers use the same API.
- **Performance impact:** Positive. Fixed 20 Hz emission instead of potentially 100 Hz sensor-driven emission.
